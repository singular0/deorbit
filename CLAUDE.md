## Clean-room rule

This is a clean-room reimplementation of the server that Neato robot vacuums connect to (the "Orbital" protocol). The **only** permitted source of protocol knowledge is the specification at `docs/ORBITAL_API_SERVER_SPEC.md`. Do not read, grep or list the robot's own client software, or anything that comes with it, wherever a copy is — looking at it would contaminate the clean room. When the spec is silent or ambiguous, choose a conservative behaviour and say so, or ask.

## Commands

```sh
pip install -e .                 # dependencies are `cryptography` and `PyYAML`; Python 3.11+
python -m unittest               # all tests (stdlib unittest, no pytest)
python -m unittest tests.test_server.LoginTests.test_login_response   # one test
python -X dev -m unittest        # also surfaces asyncio debug warnings and unclosed resources
python -m deorbit.certs [HOST ...]   # dev CA + server cert into certs/ (gitignored)
python -m deorbit [-c FILE]      # run the server; settings come from FILE, default ./deorbit.yml
docker compose up --build        # the same in a container, as the README has it
docker compose run --rm deorbit python -m deorbit.certs [HOST ...]
```

`python -m deorbit.certs` with hosts keeps the CA that is in `certs/` and reissues only the server certificate, for names other than `orbital.deorbit`, such as the production hostname a stock robot uses. A robot that rejects the certificate shows up on the console as a `TLS handshake failed` line.

The web UI is then at `http://localhost:8080`. It has no build step, and its files are read once at startup, so restart the server to see an edit to `deorbit/static/`.

There is no linter or formatter configured.

When smoke-testing the real server from a script, stop it with `kill` (SIGTERM). A process started with `&` from a non-interactive shell has SIGINT ignored, so `kill -INT` silently does nothing and the script hangs.

## Current scope

The server handles the whole wire protocol and prints every message to the console. What is persisted, in SQLite, is each robot's last `peer.state` body, the time of its last heartbeat, the body of every `maps.create` it sent, the floor plans it accepted from this server, and an event log: its logins, its disconnects, the abilities the server called on it and every message it sent other than a state. Every other handler in `services.py` returns the minimal reply that keeps a robot happy (`firmware.check` → 404 "no update", `logs.list_files` → no URLs), and a map that is stored is still answered `floorplan: false`. It has been exercised only against the scripted robot in the tests, never a real one. A web UI shows the robots, their events and their maps as pictures, and which robots are connected, and sends a connected robot one of five commands (start, pause, resume, cancel, return to base). It also reads a connected robot's schedule and adds, changes and deletes its events, each on no floor plan or on one this server had the robot keep, and gives a robot a name, which only this server knows. It has a connected robot keep a map it uploaded as a floor plan, new or in place of another, and drop one. It deletes a robot as well: its rows in the database, its key file and its session. It has no authentication. A real robot (firmware 1.7.0) has accepted start, pause, resume and return to base; cancel has not been sent to one. It has also answered `scheduling.show`; `scheduling.add`, `scheduling.update` and `scheduling.delete` have not been sent to one, and neither have `maps.promote_floorplan`, `maps.update_floorplan` and `maps.demote_floorplan`. No real robot has been deleted while it was connected, so what one does when its connection is ended that way is not known.

## Architecture

| Module | Role |
| --- | --- |
| `config.py` | settings, their defaults, and the YAML file they are read from |
| `framing.py` | 4-byte length prefix, heartbeat and close control frames |
| `auth.py` | robot registry, signature, clock-skew and replay checks |
| `session.py` | one connection: login, heartbeats, routing, `Session.call()` for robot abilities |
| `services.py` | replies to robot-originated services |
| `store.py` | SQLite database of each robot's last state, heartbeat time, events, maps, floor plans and name |
| `server.py` | TLS listener, one live session per robot, and the deleting of a robot |
| `commands.py` | the commands the web UI sends and the ability each invokes, the check of an event of a schedule, and what a floor plan is made of |
| `web.py` | HTTP listener for the web UI, its JSON, its commands, the schedule, the floor plans, the names and the request to delete a robot |
| `static/` | the web UI itself: one page, its stylesheet and its script, of which `map.js` reads a map's binaries, and the four helpers that bind a robot over USB |
| `certs.py` | development certificate generator |

The robot-facing protocol is not HTTP. It is a persistent TLS connection carrying frames of a 4-byte big-endian length plus a payload, where the payload is a JSON object or a one-byte control value (`0x06` heartbeat, `0x00` graceful close).

**Connection path.** `Server.serve_forever` accepts raw sockets and `Server._handle` performs the TLS handshake itself through `loop.connect_accepted_socket`, then builds the stream reader/writer by hand. This is deliberate: `asyncio.start_server(ssl=...)` swallows handshake failures, and a robot rejecting the certificate is the most likely first problem, so it must reach the log. Each connection then runs `Session.run` in its own task; `Server.stop` cancels those tasks.

**Session lifecycle** (`session.py`). `run` is the single place that maps every way a connection can end to a logged disconnect reason; internal code ends a session by raising `Disconnect(reason)`. The sequence is login → `Server.register` → heartbeat task → receive loop. `Server.sessions` holds at most one live session per robot; a newer login replaces the older one via `Session.close`, which aborts the transport.

**Event log.** `Session` is the only writer: `_login` adds a `login`, `run` adds the `disconnect` with the same reason it logs, and `_on_service` adds every message before its handler runs, except those for the services in `_UNLOGGED` (`peer.state`, since the `robots` table holds the latest state). `call` adds a `call` as it sends one, and `_on_response` adds the `response` to it together with the ability, which a response does not name; that is why `_pending` keeps the ability. A call that got no answer is thus a `call` alone, and a response that no call waits for is not logged. A body goes through `_redact` whatever `full` is set to. A rejected login leaves `Session.robot` unset, which is what keeps it and its disconnect out of the log, so every `login` in the table is one that was accepted.

**Two message directions, correlated separately.**

- Robot → server: `_on_service` looks `to.service` up in the `SERVICES` table. A handler is called with `(store, robot, body)` and returns `(code, body)`, or `None` for no reply. A reply is sent only when the envelope type is `request`. These are answered inline, in arrival order, so there is no pending-request map for this direction — which is also why a robot reusing one request ID across a log-upload job just works. Tests rely on the in-order handling to assert that a service got *no* reply.
- Server → robot: `Session.call(ability, params)` sends a request and awaits a future stored in `_pending` by ID. Responses may arrive in any order; pending calls fail with `ConnectionError` when the session closes. Its one caller outside the tests is the web UI's command endpoint.

**Identity and auth** (`auth.py`). A robot is identified by `RobotId(vendor, board serial)`, both lowercased, matching the string the robot signs. `Authenticator(keys=None, ...)` accepts every well-formed login without verification; with a key registry it checks the RSA signature, then clock skew and replay. Keys are loaded once at startup into a dict, so no filesystem path is ever built from a serial sent over the wire. `delete_key` keeps to that: it lists the directory as `load_keys` does (`_key_files`) and removes the files whose names come to the robot's, which may be several where names differ only in case. `Authenticator.forget` takes the key out of the dict, so a deleted robot is refused without a restart.

**Storage** (`store.py`). `Server` opens one `Store`, a single SQLite connection to the `database` file, and closes it in `stop`. The `robots` table has one row per `RobotId`, upserted by `save_state` (from the `peer.state` handler, which skips a body that is not an object) and `save_heartbeat` (from the receive loop). `save_state` keeps the whole body in `state_json`, as the JSON object the robot sent, and nothing else of it: no field of a state has a column, which is also how the spec's rule that unknown fields be preserved is met. `robots()` and `robot()` read the fields the web UI shows out of it with `json_extract`, each under the name `_STATE_FIELDS` gives it, and with them the robot's `name`, which `_ROBOTS` joins on from the `names` table. That table of names and JSON paths drives only those two SELECTs and nothing of it is in the file, so a new field is one line there, and one in the table of fields under "HTTP API" below. The spec names only the top-level state fields, so the nested ones in `_STATE_FIELDS` come from what a real robot (firmware 1.7.0) sent to this server, as printed on its console, not from the robot's own software. That the numbers in `autonomy_states` (`_AUTONOMY_STATES`) are Unix seconds, with -1 for a step not reached, is likewise read off what the robot sent (its `cleaning_start` equalled the start time in the `maps.create` of the same run); the spec does not mention them. They are given as sent, and only the page reads them as times. SQLite has no JSON type, so `state_json`, the events' `body_json` and the maps' `map_json` each carry a `CHECK (json_valid(...))`: a text the JSON functions cannot read would fail every read that touches its row, so it is refused at the write, where it costs one state. That is what turns away a non-finite number, which Python writes as the bare word `Infinity`. `_json` leaves text unescaped (`ensure_ascii=False`) for the same reason: a lone surrogate then fails to be bound, where as a `\ud800` escape it would pass `json_valid` and make `json_extract` return text that Python cannot decode. A whole number beyond SQLite's range is valid JSON and is stored as sent; `json_extract` reads it as a float, an infinity if it is long enough, which is why `web.py` has `_finite`. There is no migration code, by decision: `CREATE TABLE IF NOT EXISTS` leaves an existing table as it is, so a change to one means starting from a new file, while a table the file lacks, as `maps` once was, is added to it. That is one reason a robot's name is a table, `names`, and not a column of `robots`; the other is that a name is nothing the robot sent. The spec has no name for a robot, only the board serial of its login, which is what the UI called a robot before and still does by default: a row in `names` is a robot that was given a name, `save_name` with `None` deletes it, and the `name` a robot is read with is then NULL. Nothing keeps two robots from one name. The `events` table is the append-only event log: `add_event` inserts a row whose `id` orders them. Its `kind` is a word only this server chooses (`login`, `disconnect`, `call`, or the envelope type of a message the robot sent) and its `service` is whatever name the robot sent; the two are separate columns so that a message for a service named `login` cannot pass for a login. Nothing prunes the table: rows leave it only with their robot. `events()` reads rows back for the web UI, as stored. It gives one robot's, through the `events_by_robot` index, because the UI shows events only on a robot's own page; the store tests still check the file through a second connection. The `maps` table gets a row from `save_map` for each `maps.create`, with the whole body in `map_json`; the user asked (2026-10-08) for maps as JSON objects in a table of their own. The two binaries stay in the object as the Base64 text the robot sent, where the spec suggests decoding them into binary storage, so this is the one place they are kept: the event of the same upload has them redacted. A row is an upload, not a `rank_uuid`, which the spec does not say is unique; a real robot (firmware 1.7.0) sent a map at every pause of a run and one at its end, each under a new `rank_uuid` and all with the run's `timing.start`. `maps()` lists one robot's, through the `maps_by_robot` index, each without its two binaries: `_MAP` takes them out with `json_remove`, which leaves every number as the text it was sent as. SQLite still reads each listed map whole to do that, on every poll of a robot's page, which is why the web UI lists few at a time. `floorplan_maps()` gives the same way those of a robot's maps that a floor plan of its was made of and that are older than the map it is told, which is how the page has the map of a floor plan that is not among those few. `map()` gives one row as it is stored, and only for the robot it is asked of. The `floorplans` table is what the server remembers of the floor plans a robot keeps (see "Floor plans" below): a row for each `rank_uuid` a robot accepted from this server, with the `id` of the map it was made of, which is not copied and stays in `maps` as long as the robot does. `save_floorplan` upserts one, so a floor plan that is made again is the same row with its later map and time, `delete_floorplan` takes one out, and `floorplans()` lists one robot's, the last accepted first. Reads and writes are synchronous and run inline in the event loop: each is one autocommitted statement, a locked file is waited on for at most `_BUSY_TIMEOUT`, and the default rollback journal is kept rather than WAL so that the file also works on a Docker bind mount. Two writes are more than a statement. `delete` takes a robot's rows out of every table in `_TABLES` in a transaction it begins itself (`BEGIN IMMEDIATE` inside `with self._db`, which commits it or rolls it back), so a robot is deleted from all five or from none. `save_floorplan` does the same where a floor plan takes the place of another, so the old row goes and the new one comes, or neither. A table added to the schema has to be added to `_TABLES`, which a test checks against the file. The connection has `secure_delete` on, so what is deleted is zeroed in the file and not left in its free pages; the file does not shrink. `delete` logs its failure and says whether it wrote, like `_write`. A failed write, including a body one of those checks refuses, is logged and swallowed inside `Store`, so a storage problem never ends a session. `_write` says whether it wrote, which `save_map`, `save_name` and `delete_floorplan` pass on, and `save_floorplan` says the same of its transaction. The page that sent a name is told 503 when it was not written. A map is the one write a robot waits to hear of: the `maps.create` handler answers 201 only for a map that is in the file, 500 for one that is not, and 400 for a body that is not an object. The spec names no code for a failure, only that the robot takes any code but 201 for a failed upload, and does not say what the robot does then; neither code has been sent to a real robot. A failed read raises `StoreError`, as does failing to open the file, which `main` turns into a startup error.

**Web UI** (`web.py`, `static/`). `Web` is a second listener in the same event loop, over plain HTTP. `_serve` in `__main__.py` starts it beside the `Server` when the `web` setting is on; `Server` knows nothing of it, so the robot-protocol tests never open it. It takes three things from the `Server`: the `Store`, which it reads rows from and writes nothing to but a name and the floor plans, `Server.sessions` for whether a robot is connected (`Session.since` exists only to be shown here, and `Session.firmware` for that and for the login event) and for the session a command is sent on, and `Server.delete`. The HTTP side is written by hand because the project has no web framework among its dependencies: `GET` and `HEAD`, and `POST` alone for the paths in `_posts` (a command, the schedule, a floor plan, a name, the deleting of a robot), one request per connection (`Connection: close`), and no request body is ever read. `_TIMEOUT` is how long a connection has to send its request and, separately, to take the answer; the wait between the two is a command's for its robot, which `_COMMAND_TIMEOUT` limits. The files in `static/` are read once at startup into a table keyed by request path, so no file name is ever built from a request; `pyproject.toml` lists them as package data, which the Docker image relies on. The JSON API gives what the store reads (true and false as `1` and `0`, JSON as text) and the page interprets it; a robot is named in the query string because a vendor or serial may hold `/` or be `..`. `/api/robot` gives a robot together with its latest events and maps, as many as the `events` and `maps` parameters say, and with all its floor plans. It asks the store for one more of each than that, which is how it knows whether to say there are `more` and `more_maps`. Where there are more maps, it also gives those older ones that a floor plan was made of, as `floorplan_maps`: the page shows a floor plan as the map it was made of, so that map has to come however old it is. A number outside 1 to `_MAX_EVENTS`, or to `_MAX_MAPS`, is answered with status 400, so `EVENTS_MAX` and `MAPS_MAX` in `app.js` have to match, which a test checks. `/api/map` gives one map whole, named by its robot and its `id`; an `id` that is no number a row can have is answered 404 like any other map that is not there, and has to be turned away before the store, because `sqlite3` raises an `OverflowError`, which is no `sqlite3.Error`, for a number beyond 64 bits. A robot has a page only once it has a row in `robots`, so the events of one that logged in and sent neither a state nor a heartbeat are in the database but not in the UI.

`POST /api/name` names the robot in its query string and gives its `name` there too, so this request has no body to read either. `_name` makes one line of it (white space around it gone, a space wherever there was white space within) and refuses more than `_MAX_NAME` characters, or a control character, with a 400; these limits are this server's choice. No name, or none left, takes the robot's name away. `_rename` answers 200 with the `name` as it is kept, 404 for a robot without a row in `robots`, since a name for one would be a row nothing reads, and 503 for a name the store did not write. It sends the robot nothing and adds no event, so the robot need not be connected. It is behind `_own_page` like a command. The page's `NAME_MAX` must be `_MAX_NAME`, which a test checks.

**Deleting a robot** (`Server.delete`, `Web._delete`, `forget` in `app.js`). The user asked (2026-10-08) that a robot can be deleted, with all its data "from db and filesystem". The database is the only place this server writes anything of a robot. The one other file that is a robot's is its key under `keys`, which the operator put there; that the request covers it is my reading, and it is what makes a deleted robot stay away where logins are verified. `POST /api/delete` names the robot in its query string, has no body and is behind `_own_page`. `_delete` answers 404 for a robot without a row in `robots`, as `_rename` does, so neither the events of a robot that has no page nor the key of one that never connected can be deleted through it; 200 with `{}` once the robot is gone; and 503 with an `error` when it is not.

`Server.delete` does three things, in an order chosen for what a failure leaves behind. First the key file and the key in memory, when `keys` is set: a file that cannot be removed is an `OSError` (the 503), raised with nothing else touched, which is what a robot gets whose key is on the read-only mount `docker-compose.yml` suggests; and with the key gone first the robot cannot log in again during the rest. Then it closes every session of the robot's and waits for their tasks: a session writes to the store until `run` returns, its `disconnect` last, and a row written after the delete would be left over. It finds them in `_running`, which `_handle` keeps from the handshake to the end of `run`; `sessions` would not do, because a session that a newer login replaced is out of it before it has ended. Last, with nothing awaited since no session was found, `Store.delete`. If that fails (the other 503) the key is gone and the session ended while the rows are all there, so the robot is still listed and asking again finishes the job. Without `keys` nothing keeps a deleted robot out: it logs in again as a new one, and the loop in `delete` is for one that did so while its older session was waited for.

On the page, Delete is beside Rename at the top of a robot's page, by the user's decision (2026-10-08), so `nameLine` draws it and it is there whichever tab is shown, though not while the field for the name is open. The view's `deleting` holds whether it was pressed (`asked`), whether the server has yet to answer, and how the last request failed. The second press is asked for by `deleteQuestion`, which `hero` puts under the name: what will go, and Delete it beside Keep. That is not where the first button was, which is gone meanwhile, so that a double click deletes nothing, and the keyboard is put on Keep. A press on any of the three takes the focus to its button first, because of `entering`: the field for the name may be open under the question. `forget` sends the request and, at a 200, sets the address to the list.

**Adding a robot** (`/api/setup` in `web.py`, the add-robot part of `app.js`, and the helpers under `static/`). The user asked (2026-10-08) for an "Add robot" button on the list that points a robot at this server with `reconfigureNeato`, and later that day renamed it: the button, with the link icon, and the dialog's title both read "Bind a robot", and the dialog's first paragraph and the note under the server address are the user's wording, so change them only when asked. The names in the code still say add. The user put four browser-side helpers in `static/`: `webusb-transport.js` (WebUSB bulk transport), `mtp-client.js` (raw MTP), `mtp-fs.js` (the file system over MTP) and `neato-config.js` (`reconfigureNeato`, which rewrites the robot's `/etc/hosts`, `vendors.ini` and trusted certificate). The work is entirely in the browser, over USB: the server sends the robot nothing for this. It gives the page two things, over `GET /api/setup`: the `public_address` to write into the robot's hosts file for `orbital.deorbit`, and the CA the robot must trust, which `_ca` reads afresh as `ca.crt` beside the certificate — the certificate only, never `ca.key`, and both are public, so this is a plain GET, not behind `_own_page`. `public_address` is a `Config` field, empty by default. Where it is empty, by the user's decision (2026-10-08), `main` tries to detect it at startup with `local_address` in `config.py` and logs what it found, or warns that it found nothing. The page does not ask for the address, also by the user's decision (2026-10-08): it shows the one `/api/setup` gave and points the robot at that, so a wrong one is put right in the settings and with a restart, which the dialog says, and with none (`noAddress`) the dialog says why and connects to nothing. `local_address` takes `host`: an address the server listens on alone is the answer, unless it is the loopback, which no robot reaches; for `0.0.0.0` or `::` it is the address the system would send from to another network, asked for by connecting a UDP socket to 192.0.2.1, an address set aside for documentation, which sends nothing; a `host` that is a name is not looked up. It gives an IPv4 address or none, and a wrong one on a machine with several networks or a VPN, and in a container, where it is the container's own: the README says to set the setting there. `Web` does none of this and gives `/api/setup` what `Config` holds, so the web tests see no detected address.

All four helpers are served from `_PAGES` and packaged like the other static files; `mtp-fs.js` has no special handling (the user's decision, 2026-10-08, after an earlier `_OPTIONAL_PAGES` arrangement was dropped). It is not committed to git (see the rule above), so a build has it only where it is on disk, which is why the page loads the helpers with a dynamic `import()` only when the dialog is opened (`loadHelpers`): the rest of the UI works whether or not they are served, and the device prompt stays the first `await` of the click that starts the flow, which WebUSB needs for its gesture. With `mtp-fs.js` absent the import fails and the dialog says so. The flow is `WebUSBTransport.open` → `MtpClient.openSession` → `new MtpFileSystem(client)` with its `log` set to the dialog's → `reconfigureNeato(fs, {ip, certBytes, onConfirm, onBackup})`; the write options come from the contract `neato-config.js` documents: `onConfirm` is a `window.confirm` of the action (without it every write aborts unanswered - the default declines - which is the "aborted by user" failure the user hit on 2026-10-08), `onBackup` downloads the replaced original as a `.bak`, and an aborted result is reported as aborted rather than as a refused write; the `MtpFileSystem` line is built to the contract `neato-config.js` documents (an `MtpFileSystem` over an open session, with a `log` it calls), since `mtp-fs.js` was not read, and is the one line to correct if its exports differ. On the page the button is in the list heading (`addButton`). It is disabled, by the user's decision (2026-10-08), in a browser without WebUSB (`WEBUSB`, which is whether `navigator.usb` is there: Chrome and Edge have it, and only on a page from https or localhost), with the reason in its `title` as the page's other disabled buttons have theirs; the dialog is thus never open without WebUSB and checks for it nowhere, and the lead of an empty list does not offer adding one then. The certificate is installed on every robot, by the user's decision (2026-10-08), with nothing to tick; a server with no `ca.crt` has none to install, and the run says so in its log and goes on. The view's `adding` holds the log lines, whether it is running or done, how it failed, whether the server has yet to answer `/api/setup` (`asking`) and what it gave, which is `null` for no answer. 

What the button opens is a modal over the page with the page blurred behind it, by the user's decision (2026-10-08): the one `<dialog>` of `index.html`, shown with `showModal`, whose `::backdrop` does the blurring. It is no part of the page that `draw` builds. `drawAdd` fills it from the view's `adding` when that has changed, handing the focus on by `data-focus` as `draw` does, so a poll that draws the list anew leaves it alone, a selection in its log is not held against a redraw, and the list is drawn from the robots only. A floor plan that a robot has from the maker's cloud is not in the table either, which is why neither `demote` nor the `old_rank_uuid` of `update` is held to the table: any UUID is sent on, and the robot answers for itself.

The Floor plan column has a box that is ticked for a map which is the `map_id` of a row of the table (`kept`). The `rank_uuid` is not shown beside it, by the user's decision the same day; that it is still the box's `title` is mine, since nothing else on the tab now tells which floor plan an event of the schedule names. The box only says so; that it is not what changes it is my reading of "floorplan checkbox" beside the three buttons the user asked for. Those are in every map's row, each an icon (`mapTools`): Promote, Demote and Replace. That Promote and Replace can be pressed only on a map that is no floor plan, and Demote only on one that is, is my choice, as is that Replace needs a floor plan to replace: a row of the table or the map's own `persistent_rank_uuid`, so a floor plan the server never noted can be replaced by a map of a run on it, and demoted only through the API. The server holds none of this against a request. The maps that are floor plans stand at the top of the table, by the user's decision the same day, the one the robot accepted last first, and the others after them, newest first (`mapList`); for that the maps of floor plans come with `/api/robot` however old they are (`floorplan_maps`). A floor plan whose map is no longer in `maps`, which nothing but a hand in the file brings about, has no row.

Demote and Replace are asked twice (`askAgain`, `floorQuestion`), and the question is a line under the map's row, not where the first button is, so that a double click takes nothing from the robot: Keep, which the keyboard is put on, and beside it Demote it, or a Replace for each floor plan there is to replace, so that the second press is also what chooses among several. Keep is no `robotButton`, so it also takes the question back while the robot is away. The view's `floors` holds whether an answer is waited for, the map and the action that await their second press (`asking`), and how the last request went with the map it was pressed on, under whose row that is said (`floorSaid`), or under the table when the map is listed no more, as an old one is once it is demoted. `robotButton` is the button the schedule and the floor plans share: one that asks something of a connected robot, with an icon before its label when it is given a `glyph`, which is `alone` on a button of a row. After an answer the page calls `refresh`, since the floor plans come with `/api/robot`.

The UI has no authentication, and by the user's decision (2026-10-08) commands do not wait for one: whoever can reach the UI can command a robot. What stops another website from doing so through a visitor's browser is `_own_page`: a command must carry an `Origin` whose host and port are those of its `Host`. A browser sends `Origin` with every `POST`, so a request without one is refused as well, which is why `curl` needs `-H 'Origin: ...'`, and a reverse proxy has to pass `Host` through. The check does not stop DNS rebinding, where a site makes a name of its own resolve to this server: that would take a list of the server's own names, or a login.

**Configuration.** The `Config` dataclass in `config.py` is the single source of settings and their defaults. `load` in the same module fills it from a YAML file whose keys are the field names, converting values by each field's annotation, so a new `Config` field of an existing type (`Path`, `str`, `int`, `float`, `bool`) is settable from the file with no further code. Relative paths are resolved against the file's directory. The only command-line option is `-c/--config`; a missing file is an error unless it is the default `./deorbit.yml`, in which case `Config()` is used as is. The `deorbit.yml` at the repository root is an example listing every setting at its default, and the README's table of settings repeats it; update both when a field is added.

`generate_certs` is acted on by `main`, not by `Server`, which always expects the files to exist. An empty `public_address` is filled in by `main` the same way, and only when `web` is on, since nothing but the web UI reads it. Likewise `web`, `web_host` and `web_port` are acted on by `_serve` and `Web`. When `cert` and `key` are both missing, `main` calls `certs.generate` for `certs.DEFAULT_HOSTS` (`orbital.deorbit`); when only one is missing it exits, because generating would overwrite the other.

**Console output.** All message printing goes through `Session._trace`, which redacts the keys in `_REDACTED_KEYS` (signatures, map binaries) unless the `full` setting is on. Heartbeats are logged at DEBUG, everything else at INFO or above.

## Protocol constraints that are easy to break

These come from the spec and are not all enforced by tests:

- The server must never send an `event` to the robot — only `request` and `response`. An event makes the robot drop the connection.
- `robots.notify` arrives as a `request` but must not be answered. `peer.state` and `robots.error_codes` are events and are not answered either.
- A frame's header and payload must go out in one write (`encode_frame` returns them joined), and writes on a connection must not interleave (`Session._send` holds a lock).
- The robot disconnects after 70 seconds without a frame, and its own requests time out after 30 seconds, so handlers must reply promptly. If a handler ever needs to do slow I/O, it can no longer run inline in the receive loop.
- The login response has no `type` or `id`; a non-200 `code` makes the robot disconnect and retry.

## HTTP API

What `web.py` answers besides the files of `static/`, all of it JSON. The page is its first user; the README only says that it is there. A port that is already taken stops the server at startup.

| Address | Content |
| --- | --- |
| `GET /api/robots` | every robot without its `state_json`, ordered by vendor and serial |
| `GET /api/robot?vendor=V&serial=S` | one robot as `robot`, with its `state_json`, its latest 25 `events` and its latest 10 `maps`, both newest first, its `floorplans` and the older maps those were made of as `floorplan_maps`, or status 404; with `events=N` as many events as that, up to 1000, and with `maps=N` as many maps, up to 100 |
| `GET /api/map?vendor=V&serial=S&id=N` | one map of that robot as `map`, whole, or status 404 |
| `GET /api/setup` | what "Bind a robot" needs: the `address`, which is `public_address` as set or as found at startup and empty for none, and the `ca`, the text of `ca.crt` or `null` |

A robot has the columns of the `robots` table (see "Database" below), as stored, its `name` from the `names` table, `null` when it was given none, then the fields of its state that the pages show, and a `session`: `null` for a robot that is not connected, otherwise its `address`, `firmware` and the time `since` when it has been connected. So the page shows the address and firmware of a connection only while it lasts; those of earlier connections are in the robot's login events. The fields are read out of `state_json`:

| Field | Where in the state |
| --- | --- |
| `state`, `action`, `errors` | the fields of those names: what the robot is doing, such as `idle`, and its errors, `null` when it reports none |
| `can_start`, `can_cancel`, `can_pause`, `can_resume`, `can_return_to_base` | `available_commands` |
| `is_charging`, `is_docked`, `charge`, `base_type`, `is_quickboost`, `quickboost_estimate` | `details`; `charge` is a percentage |
| `base_error`, `bag_status`, `is_extracting` | `cleaning_center` |
| `autonomy_states` | `autonomy_states`, whole |
| `autonomy_started_on_base` | the `started_on_base` of `autonomy_states` |
| `autonomy_cleaning_start`, `autonomy_undocking`, `autonomy_active_cleaning_session`, `autonomy_docking_for_suspended`, `autonomy_docking_successful_suspended`, `autonomy_suspended_charging_start`, `autonomy_undocking_after_suspended`, `autonomy_active_cleaning_after_suspended`, `autonomy_docking`, `autonomy_docking_verify_base`, `autonomy_docking_successful` | the other fields of `autonomy_states`: when the robot reached each step of its run, in seconds since 1970 by its own clock, or -1 for a step it has not reached |

True and false are given as 1 and 0, an object or an array as JSON text, and a field the state lacks as `null`. An idle robot sends no autonomy states, which leaves theirs `null`. An event has the columns of the `events` table, as stored, and `more` says whether the robot has older events than were given. A map has the columns of the `maps` table and `more_maps` says the same of the maps. With a robot, the `map_json` of each map lacks the two binaries, which are most of it; `/api/map` gives the row as it is stored. A floor plan has the columns of the `floorplans` table, and a robot comes with all of its own, the one it accepted last first. `floorplan_maps` are the maps those were made of that are older than the `maps` given, newest first and each as `maps` gives one, so that every floor plan comes with its map; it is empty when `more_maps` is false. The answers of `/api/robots` and `/api/robot` carry the server's time as `now`. The page asks for the latest 25 events and 10 maps, and for that many more each time it is asked to show older ones.

A command is sent with `POST /api/command?vendor=V&serial=S&command=C`, where `C` is `start`, `pause`, `resume`, `cancel` or `return_to_base`. The request has no body and needs the `Origin` header a browser adds, naming the host it is sent to:

```sh
curl -X POST -H 'Origin: http://localhost:8080' 'http://localhost:8080/api/command?vendor=n&serial=SERIAL&command=pause'
```

When the robot answers, the status is 200 and the JSON holds the `ability` that was invoked with the robot's own `code` and `body`, and `sent`, the server's time when the command went out, which a later `state_at` of the robot is after; a `code` of 200 is the robot accepting the command. Otherwise the JSON holds an `error`, and the status is 403 for a request from another site, 400 for a command that is not one of the five, 409 for a robot that is not connected, 504 for one that did not answer in time, which is 10 seconds, and 502 for one whose connection ended first.

A schedule is read and changed with `POST /api/schedule?vendor=V&serial=S&action=A`, which needs the same `Origin` and is answered the same way, with the `ability` it invoked and the robot's `code` and `body`:

| `action` | With | Invokes |
| --- | --- | --- |
| `show` | nothing | `scheduling.show`; the `body` of the answer is the schedule, with its `events` |
| `add` | `event=JSON`, an event without an `id` | `scheduling.add`; the robot gives the event its `id`, which only `show` tells |
| `update` | `event=JSON`, an event with the `id` of the one it replaces | `scheduling.update` |
| `delete` | `id=N` | `scheduling.delete` |

```sh
curl -X POST -H 'Origin: http://localhost:8080' 'http://localhost:8080/api/schedule?vendor=n&serial=SERIAL&action=show'
curl -X POST -G -H 'Origin: http://localhost:8080' 'http://localhost:8080/api/schedule?vendor=n&serial=SERIAL&action=add' \
  --data-urlencode 'event={"enabled":true,"days":["mon","wed","fri"],"time":"09:30","command":{"ability":"cleaning.start","runs":[{"settings":{"mode":"eco","navigation_mode":"normal"},"map":null}]}}'
```

An event is the one of the specification, in the address like everything else of a request: `enabled`, true or false; `days`, one or more of `mon`, `tue`, `wed`, `thu`, `fri`, `sat` and `sun`; `time`, from `00:00` to `23:59`; and a `command` whose `ability` is `cleaning.start` and whose `runs` are one or more runs. A run has its `settings`, a `mode` of `eco`, `turbo`, `auto` or `max` and a `navigation_mode` of `normal` or `gentle`, and a `map` that is `null` for no floor plan or has the `rank_id` of one, a `track_id` that is `null` or a zone, and `nogo_enabled`. More runs than one must all be of the same floor plan. An `id` is a string of digits. A request the server does not take is answered 400 with an `error` that names what is wrong. A schedule also says whether it is on as a whole, which no command changes, so the page only says so when a robot gives its schedule as off.

A robot is told to keep a map as a floor plan, or to drop a floor plan, with `POST /api/floorplan?vendor=V&serial=S&action=A`, which needs the same `Origin` and is answered the same way, with the `ability` it invoked and the robot's `code` and `body`:

| `action` | With | Invokes |
| --- | --- | --- |
| `promote` | `map=N`, the `id` of a map of that robot's | `maps.promote_floorplan`: the robot keeps the map as a new floor plan, with no zones and no no-go map |
| `update` | `map=N`, and `old_rank_uuid=U` | `maps.update_floorplan`: the robot keeps the map in place of the floor plan it knows as `U` |
| `demote` | `rank_uuid=U` | `maps.demote_floorplan`: the robot deletes the floor plan it knows as `U`, with its zones |

```sh
curl -X POST -H 'Origin: http://localhost:8080' 'http://localhost:8080/api/floorplan?vendor=n&serial=SERIAL&action=promote&map=5'
curl -X POST -H 'Origin: http://localhost:8080' 'http://localhost:8080/api/floorplan?vendor=n&serial=SERIAL&action=demote&rank_uuid=414fb561-91a7-4a95-8fc7-200169d2d5af'
```

The floor plan has the `rank_uuid` of its map, the map's two binaries and the place of its base, and says it was made when the request came. A `code` of 200 is the robot accepting, and only then do the `floorplans` that come with the robot change: they are what this server had the robot make, not what the robot holds, which it cannot be asked for. So `U` need not be one of them: a floor plan the robot has from elsewhere, such as the `persistent_rank_uuid` of a map or the `rank_id` in its schedule, is named the same way. The status is 404 for a map that is not in the database, 400 with an `error` that names what is wrong for an `action` that is none of the three, a `U` that is not a UUID or a map that lacks what a floor plan takes, and 503 when the robot accepted and the database could not be written, after which the request can be sent again. The other statuses are those of a command.

A robot is named with `POST /api/name?vendor=V&serial=S&name=NAME`, which needs the same `Origin` and sends the robot nothing:

```sh
curl -X POST -G -H 'Origin: http://localhost:8080' 'http://localhost:8080/api/name?vendor=n&serial=SERIAL' \
  --data-urlencode 'name=Living room'
```

The answer is 200 with the `name` as it is kept, which is `null` when nothing is left of it or when the request has no `name`. Otherwise the JSON holds an `error`, and the status is 400 for a name of more than 64 characters or with a control character in it, 404 for a robot that is not in the database and 503 for a name the database did not take.

A robot is deleted with `POST /api/delete?vendor=V&serial=S`, which needs the same `Origin`:

```sh
curl -X POST -H 'Origin: http://localhost:8080' 'http://localhost:8080/api/delete?vendor=n&serial=SERIAL'
```

The answer is 200 with an empty object once the robot is gone, 404 for a robot that is not in the database and 503 for one that could not be deleted. The robot is still listed after a 503, so the request can be sent again.

## Database

What is in the `database` file, which is created with its directory at the first start. Times are UTC, written like `2026-10-08T13:55:37.511Z`. The `robots` table has one row per robot that has connected:

| Column | Content |
| --- | --- |
| `vendor`, `serial` | the robot, as the log names it: `[<vendor>/<board serial>]`, both in lowercase |
| `heartbeat_at` | when the robot's last heartbeat arrived; robots send one a minute |
| `state_at` | when the robot's last state arrived |
| `state_json` | that state, whole: the JSON object the robot sent |

Each state replaces the one before it entirely, and `state_json` is empty before the robot has sent one. SQLite's JSON functions read a field out of it, which is how to ask the file, also while the server runs:

```sh
sqlite3 data/deorbit.db "SELECT serial, state_json ->> '$.state', state_json ->> '$.details.charge', state_at FROM robots"
sqlite3 data/deorbit.db "SELECT serial FROM robots WHERE state_json ->> '$.details.is_docked' = 0"
sqlite3 data/deorbit.db "SELECT serial, datetime(state_json ->> '$.autonomy_states.cleaning_start', 'unixepoch') FROM robots"
```

`->>` needs SQLite 3.38 or later; `json_extract(state_json, '$.state')` reads the same from an older one. True and false come out as 1 and 0. The store tests ask the file this way through a second connection.

The `names` table holds the `vendor` and `serial` of each robot that was given a name, and that `name`. A robot that goes by its serial has no row.

The `events` table gets a row when a robot logs in, when its connection ends, when the server calls one of the robot's abilities, and for each message the robot sends other than a state and a heartbeat:

| Column | Content |
| --- | --- |
| `id` | a number that counts up: the order the events were recorded in |
| `at` | when the event was recorded |
| `vendor`, `serial` | the robot |
| `kind` | `login`, `disconnect`, `call` for an ability the server called, or the type of the robot's message: `request`, `event`, or `response` for its answer to a call |
| `service` | the service a request or an event was for, such as `robots.notify`; empty for the other kinds |
| `body_json` | the message's body as JSON, empty if it had none; for a login its `address`, its `firmware` and whether its signature was `verified`; for a disconnect the `reason`; for a call what the robot was sent, which names the `ability`; for a response that `ability` and the robot's `code` and `body` |

Signatures and map binaries are replaced by their length, like `<2048 chars>`. A body is read the way a state is, and since nothing prunes the table, this is also how to drop what is older than 30 days:

```sh
sqlite3 data/deorbit.db "SELECT at, body_json ->> '$.message_code' FROM events WHERE service = 'robots.notify'"
sqlite3 data/deorbit.db "DELETE FROM events WHERE at < date('now', '-30 days')"
```

The `maps` table gets a row for each `maps.create`, which a robot sends when a cleaning run ends or is interrupted:

| Column | Content |
| --- | --- |
| `id` | a number that counts up: the order the maps arrived in |
| `at` | when the map arrived |
| `vendor`, `serial` | the robot |
| `map_json` | the map, whole: the JSON object the robot sent |

Here the object has its two binaries, `rank_binary` and `real_binary` under `map`, each a compressed PGM file as Base64 text. The rest of the object is read the way a state is, and a binary comes out with `base64`, and as a PGM file once it is inflated:

```sh
sqlite3 data/deorbit.db "SELECT id, at, serial, map_json ->> '$.rank_uuid', map_json ->> '$.cleaning_complete', map_json ->> '$.runs[0].state' FROM maps"
sqlite3 data/deorbit.db "SELECT map_json ->> '$.map.real_binary' FROM maps WHERE id = 1" | base64 -d > real_binary
sqlite3 data/deorbit.db "SELECT map_json ->> '$.map.rank_binary' FROM maps WHERE id = 1" | base64 -d | python3 -c "import sys, zlib; sys.stdout.buffer.write(zlib.decompress(sys.stdin.buffer.read()))" > rank.pgm
```

The `floorplans` table gets a row when a robot accepts a map as a floor plan from this server, and loses it when the robot accepts that it is to drop that floor plan, or takes another in its place:

| Column | Content |
| --- | --- |
| `vendor`, `serial` | the robot |
| `rank_uuid` | what the robot knows the floor plan by: the `rank_uuid` of the map it was made of |
| `map_id` | that map, by its `id` in the `maps` table |
| `at` | when the robot accepted it |

A robot has one row for each `rank_uuid`. The table is the server's record and not the robot's: a floor plan the robot was given by anything else is not in it.

```sh
sqlite3 data/deorbit.db "SELECT f.serial, f.rank_uuid, f.at, m.at, m.map_json ->> '$.timing.start' FROM floorplans f JOIN maps m ON m.id = f.map_id"
```

A state, a map or a body that is not stored because SQLite could not read it back as JSON is one with a number such as `1e999`, too large for the server to read as a number at all, or with text that is not Unicode.

## Tests

`tests/test_server.py` is end-to-end: a scripted `Robot` talks to a real `Server` over TLS on an ephemeral port, with certificates and a robot key generated once per test class. `ServerTestCase.start(**overrides)` takes `Config` field overrides, which is how tests shorten `heartbeat_interval`, `idle_timeout` and similar. `login()` returns both the wire-side `Robot` and the server-side `Session`, so a test can drive either end. Each test gets its own database file, named after the test, in the class's temporary directory.

`tests/test_config.py` covers the settings file. Its command-line cases call `main()` through a helper that patches out `_serve` and `logging.basicConfig`, so no server is started and no console handler outlives the test; a case that would otherwise generate a certificate does so inside its temporary directory. The helper also puts a mock in place of `local_address`, which finds no address unless a test says so, because the machine the tests run on has whatever address it has; `LocalAddressTests` is the function itself, with a mock for the socket in all but one test.

`tests/test_store.py` drives a `Store` directly and checks what it leaves in the file.

`tests/test_web.py` starts a `Web` beside the `Server` of `ServerTestCase` and speaks HTTP to it over a raw connection, which is what lets it send malformed requests and choose the `Host` and `Origin` of a command; `api()` fails on JSON a browser would refuse. `CommandTests` has the scripted robot answer each command, and relies on the in-order handling the same way to show that a refused request sent the robot nothing. `NameTests` is `/api/name`, with a trigger made through a second connection for a file that takes no write. `DeleteTests` is `/api/delete`, and the class of that name in `test_server.py` is `Server.delete` itself. A test that deletes a robot while logins are verified starts its server on `registry()`, a copy of the class's directory of keys made for that test, because the class's own is shared by all its tests; a key file that cannot be removed is a patched `Path.unlink`. `ScheduleTests` does both for `/api/schedule`; its one long test is the list of everything `scheduling` refuses, each with the `error` it is refused with. `FloorplanTests` is `/api/floorplan` the same way, and stores a map for each thing `floorplan` refuses of one. `ServeTests` runs `_serve` itself. The page's script has no automated tests: after changing `static/`, look at it in a browser against a database with robots in several states. `map.js` can be tried without one: under Node, `readBinary` and `paint` take a binary out of the `maps` table and give the pixels, which is how they were checked against the real maps.
