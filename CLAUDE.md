## Clean-room rule

This is a clean-room reimplementation of the server that Neato robot vacuums connect to (the "Orbital" protocol). The **only** permitted source of protocol knowledge is the specification at `docs/ORBITAL_API_SERVER_SPEC.md`. Do not read, grep or list the robot's own client software, or anything that comes with it, wherever a copy is — looking at it would contaminate the clean room. When the spec is silent or ambiguous, choose a conservative behaviour and say so, or ask.

## Do not read `mtp-fs.js`

Never read the contents of a file named `mtp-fs.js`, wherever it is: no Read, `cat`, `grep` or any other tool, and none through a subagent, whose prompt has to carry this rule. A search over a directory that may hold it must exclude it by name, since a match would print its lines. Seeing its name in a listing, or asserting on the length of an HTTP response that carries it, is not reading it. The user gave the rule (2026-10-08) and later the reason, which the README repeats: it contains an exploit that the Vacuula team (https://github.com/vacuula) is in the process of disclosing to Vorwerk. It is in `deorbit/static/`, where the user put it; if a task seems to need what is in it, say what is missing and leave it unread.

Distributing it is allowed (user): the web UI serves it from `_PAGES` like any other file of `static/`, and a wheel or Docker image carries it when it is on disk at build time (`static/*` in `pyproject.toml`; nothing excludes it). The Docker build stops without it (user, 2026-10-19): a `RUN` before the `pip install` prints that it is missing, why it is withheld from the source and to put it in `deorbit/static/`, and exits 1. A wheel or `pip install` is still made without it. It is not committed to git: `.gitignore` names it, which stops only a plain `git add`, so when it is in the working tree check that it is not staged before a commit, and never force-add it. Commit it only if the user asks for that in plain words.

## Commands

```sh
pip install -e .                 # dependencies are `aiomqtt`, `cryptography` and `PyYAML`; Python 3.11+
python -m unittest               # all tests (stdlib unittest, no pytest)
python -m unittest tests.test_server.LoginTests.test_login_response   # one test
python -X dev -m unittest        # also surfaces asyncio debug warnings and unclosed resources
python -m deorbit.certs [HOST ...]   # dev CA + server cert into certs/ (gitignored)
python -m deorbit [-c FILE]      # run the server; settings come from FILE, default ./deorbit.yml
docker compose up --build        # the same in a container, as the README has it
docker compose run --rm deorbit python -m deorbit.certs [HOST ...]
```

- `python -m deorbit.certs` with hosts keeps the CA in `certs/` and reissues only the server certificate, for names other than `orbital.deorbit`, such as the production hostname a stock robot uses. A robot that rejects the certificate shows on the console as a `TLS handshake failed` line.
- The web UI is at `http://localhost:8080`. It has no build step, and `static/` is read once at startup, so restart the server to see an edit, which an open page then offers to reload.
- There is no linter or formatter.
- Stop a server smoke-tested from a script with `kill` (SIGTERM): a process started with `&` from a non-interactive shell ignores SIGINT, so `kill -INT` does nothing and the script hangs.

## Current scope

The server handles the whole wire protocol and logs what robots do, every message at the `debug` level. SQLite keeps each robot's last `peer.state`, the time of its last heartbeat, every `maps.create` body, the floor plans it accepted from this server with the zones and no-go lines it accepted for them, the names given to robots and maps, and an event log: logins, disconnects, the abilities the server called and every message the robot sent other than a state. The other handlers in `services.py` give the minimal reply that keeps a robot happy (`firmware.check` → 404 "no update", `logs.list_files` → no URLs), and a stored map is still answered `floorplan: false`. There is no authentication.

The web UI shows the robots, which are connected, their events and their maps as pictures. It sends a connected robot six commands (start, pause, resume, cancel, return to base, find me), a start in a given mode and navigation, on no floor plan or one this server had the robot keep, whole or one of its zones. It reads a robot's schedule and adds, changes and deletes its events, on the same choice of floor plans and zones; reads and changes its language, whether it forces its floor plan and whether it updates its software by itself; names robots and maps (only this server knows the names); deletes a map that is no floor plan's, from this server alone; has a robot keep an uploaded map as a floor plan, new or in place of another, and drop one; draws zones and no-go lines on a floor plan's picture and has the robot keep and drop them; deletes a robot (its rows, its key file, its session); and binds a robot to this server over WebUSB. Home Assistant gets the robots over MQTT discovery: a vacuum it starts, pauses, stops, sends home and has play its sound, in the mode its fan speed gives; battery, charging, docked, connected and errors as sensors; alerts and notifications as events; zones as rooms. The UI shows whether the server is connected to the broker.

What has met a real robot (firmware 1.7.0); everything else only the scripted robot of the tests:

- Commands: accepted start, pause, resume, cancel, return to base, and a start chosen in the Start menu. `utilities.find_me` has not been sent.
- Schedule: answered `scheduling.show` and accepted `scheduling.update`; `scheduling.add` and `scheduling.delete` not sent.
- Floor plans: accepted `maps.promote_floorplan` and `maps.save_track`, then acknowledged a start on that zone and raised `pm_load_fail`: the zone was an 8-bit file of maxval 255, which the robot's 16-bit track reader refuses (see "Zones and no-go lines"). No zone or no-go lines drawn as they now are have been sent, and neither have `maps.update_floorplan`, `maps.demote_floorplan` and `maps.delete_track`.
- Settings: answered `settings.robot_language`, `settings.cleaning_options` and `settings.ota_updates`; failed `settings.sounds`, no longer sent, with a 503; accepted `settings.set_ota_updates`. The other two setters have not been sent.
- No real robot has been deleted while connected, so what one does when its connection is ended that way is not known.
- No Home Assistant has met the MQTT side: only the tests' broker, and a Mosquitto it published a copy of the database to.

## Architecture

| Module | Role |
| --- | --- |
| `config.py` | settings, their defaults, the YAML file they are read from, `local_address` |
| `framing.py` | 4-byte length prefix, heartbeat and close control frames |
| `auth.py` | robot registry, signature, clock-skew and replay checks |
| `session.py` | one connection: login, heartbeats, routing, `Session.call()` for robot abilities |
| `services.py` | replies to robot-originated services |
| `store.py` | SQLite: states, heartbeats, events, maps, floor plans, tracks, names |
| `server.py` | TLS listener, one live session per robot, deleting a robot |
| `commands.py` | what the web UI and Home Assistant send and its checks: commands, schedule events, settings, floor plans, drawing zones and no-go lines |
| `mqtt.py` | Home Assistant over an MQTT broker |
| `web.py` | HTTP listener: static files, JSON API, the POST endpoints |
| `static/` | the web UI: one page, its stylesheet, `app.js`, `map.js` (reads map binaries), `theme.js` (colour scheme) and the four USB binding helpers |
| `certs.py` | development certificate generator |

The robot-facing protocol is not HTTP: a persistent TLS connection carrying frames of a 4-byte big-endian length plus a payload, which is a JSON object or one control byte (`0x06` heartbeat, `0x00` graceful close).

**Connection path.** `Server.serve_forever` accepts raw sockets and `Server._handle` does the TLS handshake itself through `loop.connect_accepted_socket`, building the stream reader/writer by hand, because `asyncio.start_server(ssl=...)` swallows handshake failures and a robot rejecting the certificate is the likeliest first problem. `_handle` turns Nagle off (`TCP_NODELAY`) before the handshake: asyncio does that only for a socket whose `proto` is TCP, and `socket.create_server` makes the listener, and so every accepted socket, with 0. Each connection runs `Session.run` in its own task; `Server.stop` cancels them. A session's address is the socket's peer, which is all the server has of it: no message of the spec carries it, `info.wifi` giving a fixed `ip`. So `docker-compose.yml` runs the container on the host's network (`network_mode: host`, user, 2026-10-29), Docker's port forwarding having given every robot of the deployed server the bridge's gateway, `172.17.0.1`; with Docker Desktop, whose VM stands between, the README has its owners publish the ports instead.

**Session lifecycle.** `run` is the one place that maps every way a connection ends to a logged disconnect reason; internal code ends a session by raising `Disconnect(reason)`. The sequence is login → `Server.register` → heartbeat task → receive loop. `Server.sessions` holds at most one live session per robot; a newer login replaces the older through `Session.close`, which aborts the transport.

**Event log.** `Session` is the only writer: `_login` adds a `login`, `run` the `disconnect` with the reason it logs, `_on_service` every message before its handler runs except services in `_UNLOGGED` (`peer.state`, which `robots` holds). `call` adds a `call` and `_on_response` the `response` with its ability, which a response does not name, hence `_pending` keeps it. An unanswered call is a `call` alone; a response no call waits for is not logged. Bodies go through `_redact` whatever `log_level` says. A rejected login leaves `Session.robot` unset, which keeps it and its disconnect out of the log, so every `login` row was accepted.

**Two message directions, correlated separately.**

- Robot → server: `_on_service` looks `to.service` up in `SERVICES`. A handler gets `(store, robot, body)` and returns `(code, body)`, or `None` for no reply; a reply goes only for envelope type `request`. Handled inline in arrival order, so there is no pending map: a robot reusing one request ID across a log-upload job just works, and tests rely on the order to assert that a service got *no* reply.
- Server → robot: `Session.call(ability, params)` sends a request and awaits a future in `_pending` by ID. Responses may come in any order; pending calls fail with `ConnectionError` when the session closes. Callers outside the tests: `Web._call` and `Mqtt`.

**Identity and auth.** A robot is `RobotId(vendor, board serial)`, both lowercased, matching the string it signs. `Authenticator(keys=None, ...)` accepts every well-formed login unverified; with a key registry it checks the RSA signature, then clock skew and replay. Keys are loaded once at startup into a dict, so no path is ever built from a serial off the wire. `delete_key` keeps to that: it lists the directory as `load_keys` does (`_key_files`) and removes the files whose names come to the robot's, several where they differ only in case. `Authenticator.forget` drops the key from the dict, so a deleted robot is refused without a restart.

**Configuration.** The `Config` dataclass in `config.py` is the single source of settings and defaults. `load` fills it from a YAML file keyed by field names, converting by each field's annotation, so a new field of an existing type (`Path`, `str`, `int`, `float`, `bool`) is settable with no further code. Relative paths resolve against the file's directory. The only command-line option is `-c/--config`; a missing file is an error unless it is the default `./deorbit.yml`, and then `Config()` is used. `deorbit.yml` at the root lists every setting at its default and the README's table of settings repeats it: update both when a field is added. `load` refuses an `mqtt_topic` or `mqtt_discovery_prefix` with a wildcard or an empty level, since each begins subscribed topics, and a `log_level` that is no key of `LOG_LEVELS`, in lowercase. `main`, not `Server`, which expects the files, acts on `generate_certs`: with `cert` and `key` both missing it calls `certs.generate` for `certs.DEFAULT_HOSTS` (`orbital.deorbit`); with one missing it exits, because generating would overwrite the other. `main` also fills an empty `public_address`, only with `web` on. `web`, `web_host` and `web_port` are acted on by `_serve` and `Web`, the `mqtt_` settings by `_serve` and `Mqtt`. A web port already taken stops the server at startup.

**Console output.** `log_level` (user), in place of `full` and `verbose`, which are now unknown settings like any other (user), is `error`, `warning`, `info` (the default), `debug` or `trace`, the last `TRACE` (5) of `config.py`, below DEBUG. It sets the `deorbit` loggers alone; `main` sets the root, which libraries log to, to WARNING (user), as aiomqtt has paho log every packet at DEBUG. A line's level does not change with the setting, which says only which lines show and how much a session's line carries: `Session._trace` logs a summary, and from DEBUG on the message after it as compact JSON on the same line (user), with `_REDACTED_KEYS` (signatures, map and track binaries) as their length below TRACE. Which line has which level (user, 2026-10-29):

- INFO, what is news, one line each and no message (user: "notable only"): startup; a login; a disconnect but for a fault; the answer of each call, 200, with who asked, `Session.call`'s `origin` (`the web UI`, `Home Assistant`, whose own lines of a call went); a line from the handler of every service in `services.py` but `peer.state`, a state being no news; what the web UI renames and deletes; Home Assistant's connection and fan speed. The certificate `main` generates is INFO too (user: "not development, just server certificate").
- WARNING: a call answered anything but 200, or not at all in time or before its session ended (user); a robot's alert, whatever its severity, an error being the server's own (user); a disconnect for a fault (user): a rejected login, invalid JSON, a frame that is no object or too large, an internal error, `Disconnect.fault` saying so of the first three; a TLS handshake that failed; anything the robot or Home Assistant sent that the server does not take; no robot keys; no `public_address` found.
- ERROR: the server's own failures, of the database, of a session (with the traceback) and of accepting.
- DEBUG: every frame each way, the login and the answers to the robot's requests included; heartbeats; the TLS connection before its login; every HTTP request (user) as the client's address, the request line quoted, as anyone may send anything, the status and the time to answer; every MQTT message (user), its topic, whether retained, and its size.

### Storage (`store.py`)

- `Server` opens one `Store`, a single SQLite connection to the `database` file, and closes it in `stop`. Reads and writes are synchronous and inline in the event loop, each one autocommitted statement; a locked file is waited on for at most `_BUSY_TIMEOUT`; the rollback journal is kept rather than WAL so the file works on a Docker bind mount.
- `robots` has one row per `RobotId`, upserted by `save_state` (from `peer.state`, which skips a body that is not an object) and `save_heartbeat`. The whole state is kept in `state_json` and nothing else of it, no column per field, which is also how the spec's rule to preserve unknown fields is met. `robots()` and `robot()` read the shown fields with `json_extract`, named by `_STATE_FIELDS`, and the `name` that `_ROBOTS` joins from `names`; a new field is one line there and one row in the field table under "HTTP API". The spec names only top-level fields, so the nested ones come from what a real robot (1.7.0) sent, as printed on the console. That the `autonomy_states` (`_AUTONOMY_STATES`) are Unix seconds, -1 for a step not reached, is read off the same robot (its `cleaning_start` equalled the `timing.start` of that run's `maps.create`); they are given as sent and only the page reads them as times.
- `state_json`, `body_json` and `map_json` each have `CHECK (json_valid(...))`: text the JSON functions cannot read would fail every read of its row, so it is refused at the write. That turns away a non-finite number, which Python writes as `Infinity`. `_json` keeps `ensure_ascii=False` so that a lone surrogate fails to bind, where as a `\ud800` escape it would pass `json_valid` and make `json_extract` return text Python cannot decode. A whole number beyond SQLite's range is stored as sent and read by `json_extract` as a float, maybe infinite, hence `_finite` in `web.py`.
- No migration code, by decision: `CREATE TABLE IF NOT EXISTS` leaves an existing table as it is, so changing one means a new file, while a missing table is added. That is one reason names are tables and not columns; the other is that a name is nothing the robot sent. `names` has a row per robot given a name (the spec has none; a robot goes by its board serial), `map_names` one per map given a name (user), by its `id` in `maps`; a map without one goes by its run's start time. `save_name` and `save_map_name` with `None` delete the row. Nothing keeps two robots, or two maps, from one name.
- `events` is append-only (`add_event`); `id` orders it. `kind` is a word only this server chooses (`login`, `disconnect`, `call`, or the robot's envelope type) and `service` whatever the robot sent, in separate columns so a service named `login` cannot pass for a login. Nothing prunes it; rows leave only with their robot. `events()` reads one robot's through `events_by_robot`.
- `maps` gets a row from `save_map` per `maps.create`, the whole body in `map_json` (user: maps as JSON objects in a table of their own). The binaries stay as the robot's Base64 text, where the spec suggests binary storage; this is their only copy, since the upload's event has them redacted. A row is one upload, and a `rank_uuid` is one upload: a real robot sent a map at every pause of a run and one at its end, each under a new `rank_uuid` and all with the run's `timing.start`, and the spec has a robot resend an upload under its `rank_uuid` when the answer was lost, which a server SHOULD take for the one it has (7.3). So the handler stores no map of a `rank_uuid` the robot already has a map of, and answers it 201 again; `has_map` asks through the index `maps_by_rank_uuid` on the expression `_RANK_UUID`, written the same way in the query so the index is used. A map whose `rank_uuid` is not text is stored each time, and so is one whose `has_map` failed, which is logged: a map twice beats a map lost.
- `maps()` lists one robot's (`maps_by_robot`) without the binaries (`_MAP`, `json_remove`, which keeps numbers as their sent text) and with the name by a subquery on `map_names`, where a join would make every query that lists maps name its columns by table. SQLite still reads each listed map whole on every poll of a robot's page, which is why the UI lists few at a time. `floorplan_maps()` gives the maps floor plans were made of that are older than a given map; `map()` one row as stored, without a name, only for the robot asked; `map_names()` the `rank_uuid` and name of each named map, for the events of uploads.
- `delete_map` takes out a map with its name (user: "would it be possible to implement map delete?"). No ability has a robot delete an upload, so this is the server's alone, and a robot that sends the map again, as one does an upload whose answer it lost (7.3), has it stored anew. `maps` has no `AUTOINCREMENT`, which no migration can add, so SQLite gives the next map the `id` of the last one if that is the one deleted: hence `_making` and `forgetMaps` (see the web server and Maps).
- `floorplans` has a row per `rank_uuid` a robot accepted from this server, with the `map_id` it was made of (not copied; it stays in `maps`). `save_floorplan` upserts, so a floor plan made again is the same row with its later map and time; `delete_floorplan`; `floorplans()` lists the last accepted first.
- `tracks` has a row per `track_uuid` a robot accepted from this server: its floor plan, `type`, a zone's name and mode, and what was drawn as `shape_json`, which the robot got only as a picture and cannot give back. `save_track` upserts, `delete_tracks`, and `tracks()` lists by floor plan, zones first, in `rowid` order: the upsert of a changed zone keeps its row, so a zone keeps its place and its colour on the page whatever it is renamed or redrawn to. A `VACUUM` could renumber the rows; nothing runs one. A floor plan's tracks go with it: `delete_floorplan` takes them out, and `save_floorplan` takes out those of the floor plan it notes, since a promotion comes with no tracks. On an update the replaced floor plan's tracks keep their rows and go to the one that replaces it, since a robot keeps them in effect (6.3, extended by the user 2026-10-18; the spec has that unverified on 1.7.0, and no update has been sent to a real robot). The new floor plan's own earlier tracks, if it was one already, are dropped, as what a robot does with them is not known.
- Writes of more than one statement: `delete` takes a robot out of every table in `_TABLES` in one transaction (`BEGIN IMMEDIATE` inside `with self._db`, which commits or rolls back), and `save_floorplan`, `delete_floorplan` and `delete_map` go through `_change`, which does the same with its statements, so a floor plan and its tracks, or an old floor plan and its replacement, change together or not at all. A new table must be added to `_TABLES`; a test checks it against the file. `secure_delete` is on, so deleted data is zeroed in the file, which does not shrink.
- A failed write, including one a `CHECK` refuses, is logged and swallowed, so storage never ends a session. `_write` says whether it wrote, passed on by `save_map`, `save_name`, `save_map_name`, `save_track` and `delete_tracks`; `_change` and `delete` say the same. A name not written is a 503 to the page. A map is the one write a robot waits on: `maps.create` answers 201 only for a map in the file, 500 for one that is not, 400 for a body that is not an object. The spec names no failure code, only that a robot takes any code but 201 as a failed upload, which it logs and never resends (7.3), so that map is lost; neither code has met a real robot. A failed read raises `StoreError`, as does failing to open the file, which `main` turns into a startup error.
- `watch` registers a function called with a robot after every write of something of it, by `_write`, `_change` and `delete`, whether or not the write succeeded, since logins and logouts are writes. It runs inside the write, so it only takes note; that is how `Mqtt` hears of changes. `last_event` (the last event `id` of any robot) and `alerts` (every robot's `robots.error_codes` and `robots.notify` events after an `id`, oldest first) are for `Mqtt` too.

### Web server (`web.py`)

- `Web` is a second listener, plain HTTP, in the same event loop. `_serve` in `__main__.py` starts it beside the `Server` when `web` is on; `Server` knows nothing of it, so the protocol tests never open it. It takes from the `Server` the `Store` (it writes nothing but names, floor plans and tracks, and deletes maps), `Server.sessions` (for whether a robot is connected, `Session.since` and `Session.firmware` being there to be shown, and for the session a call goes on) and `Server.delete`; and from `_serve` the `Mqtt`, where there is one.
- The HTTP side is written by hand, the project having no web framework: `GET` and `HEAD`, and `POST` for the paths in `_posts` alone; one request per connection (`Connection: close`); no request body is ever read, so every parameter is in the query string, which `_MAX_HEAD` limits, and a robot is named there because a vendor or serial may hold `/` or be `..`. `_TIMEOUT` bounds receiving the request and, separately, sending the answer; the wait between is a call's, `_COMMAND_TIMEOUT`.
- The files of `static/` are read once at startup into a table keyed by request path, so no file name is built from a request; `pyproject.toml` lists them as package data, which the Docker image relies on. `_version` is the first 16 hex digits of a SHA-256 over every file of `_PAGES` with its path and length, `mtp-fs.js` included, which the server reads to serve it. It is written into `index.html` in place of `{version}` (`_VERSION_MARK`) as a `meta` named `deorbit-version`, and given as `version` with every `/api/robots` and `/api/robot`, so an open page can tell it is out of date.
- The JSON API gives what the store reads (true and false as 1 and 0, JSON as text) and the page interprets it. `/api/robot` asks the store for one more event and map than asked, to know `more` and `more_maps`, and where there are more maps adds `floorplan_maps`, since the page shows a floor plan as its map, however old. A count outside 1 to `_MAX_EVENTS` or `_MAX_MAPS` is a 400. `/api/map` answers an `id` that no row can have 404 before the store, because `sqlite3` raises `OverflowError`, no `sqlite3.Error`, beyond 64 bits. A robot has a page only once it has a row in `robots`, so the events of one that logged in and sent neither a state nor a heartbeat are not in the UI.
- `_call` is shared by every endpoint that calls a robot: it invokes the ability on the live session and answers 200 with the robot's `code` and `body`, or an `error` with a status (see "HTTP API"). It names the web UI to the session as who asked, for the log. It takes a `noted`, called once the robot answers 200, which is how floor plans and tracks are recorded. An answer after `_COMMAND_TIMEOUT` is nobody's: the page was told 504 and nothing is noted.
- `POST /api/name` and `/api/map_name`: `_name` makes one line of the name (white space around it gone, a space for any run within) and refuses more than `_MAX_NAME` characters or a control character with a 400 (the same limit for maps); none left removes the name. `_rename` answers 200 with the `name` as kept, 404 for a robot without a row in `robots` (a name would be a row nothing reads), 503 for one not written; `_rename_map` the same, 404 for an `id` that is no map of the robot's, which it reads whole to know. Neither sends the robot anything or adds an event, so the robot need not be connected. The robot knows nothing of names; a floor plan is called what its map is called.
- `POST /api/map_delete`: `_delete_map` answers 404 for an `id` that is no map of the robot's; 409 for the map of a row of `floorplans`, which the page shows as the floor plan and draws its tracks on, so it goes only once demoted; 409 too while `_floorplan` waits for the robot to promote it or put it in another's place (`_making`, a list since two pages may ask at once), so that the floor plan noted after is not of a map gone, or of a later one given its `id`; 503 for one not deleted; else 200 `{}`. Like a rename it sends the robot nothing, needs no connection and adds no event.
- No authentication, and commands do not wait for one (user): whoever reaches the UI commands the robots. What stops another site doing so through a visitor's browser is `_own_page`, in front of every `POST`: the `Origin` must have the host and port of the `Host`. A browser sends `Origin` with every `POST`, so a request without one is refused too, which is why `curl` needs `-H 'Origin: ...'` and a reverse proxy must pass `Host` through. It does not stop DNS rebinding, which would need a list of the server's own names, or a login.

### Commands (`commands.py`, `Web._command`)

- `COMMANDS` gives the ability and parameters of each command, named as `available_commands` names them. `command` turns a request into the ability and what is sent, or a `ValueError` whose text is the 400's `error`; `_command` hands them to `_call`. It does not look at the `can_*` fields: the stored state may be stale and the robot answers for itself.
- Bodies follow spec 6.1, and `find_me` 6.4. `cleaning.start` takes `runs`, each a `CleaningRun` of `settings` and `map`. Without a `run` it is one run with a `map` of `null`, a non-persistent cleaning, in `eco` with `normal` navigation. A `run` is checked by `_run`, as a run of a schedule event is, and sent built anew; its `rank_id` is not held to `floorplans`; a `run` with another command is refused. The UI gives a start one run, where the spec takes several, the zones of one floor plan (`cleaning` builds those, for Home Assistant), and never sends `force_floorplan`, which the spec has a robot replace with its own setting for a server's start. The other five take nothing beyond `ability`.
- 200 with `{}` is the one code taken for success. A start on a floor plan or zone the robot lacks is 422 `{}` (spec), which the page says where the run named one. A 200 to a start only acknowledges it (6.1): a robot that cannot then load the floor plan, zone or no-go lines does not clean and says so with the alert `pm_load_fail`, as a `robots.error_codes` event, a `robots.notify` when new and an error in its status. So for `START_WATCH_MS` after an accepted start the view's `started` has the page look (`startFailed`) for that event or notification after the start's `sent`, or the error in a status after it where the status before had none, since an alert may linger. Found, it replaces the toast of the start and stays. The server does nothing of this.
- Spec 6.5: a server must validate a command body itself and not lean on the robot's traceback. A test checks the shape of the constant bodies; `command` checks the built ones.
- Find me (user: "implement find robot by sound"): `utilities.find_me`, nothing beyond `ability`, answered `{}` once the robot asked for its audible locator. The command is `find_me`, its action's name; a state has no `can_` field for it. It changes nothing of what the robot would accept, so on the page it starts no wait for a status and drops no watch of a start.

### Schedule (`commands.scheduling`, `Web._schedule`)

- The robot keeps its schedule and the server stores none of it; no message of the spec has a robot send it, so it is read with `scheduling.show` from a live session, and there is none for a robot that is not connected. `show` is a `POST` behind `_own_page` like the rest, being a call to the robot and two rows of its events.
- `scheduling` checks everything, since a robot may drop a malformed body without a word (6.5): an event is built anew from checked values, and a field the spec does not give is refused, not dropped. That includes `force_floorplan` and `auto_localization`, which a robot gives in the `command` of an event it shows and an update ignores, so the page sends back only the `runs`. `json.loads` raises `RecursionError`, no `ValueError`, for brackets nested too deep.
- Choices where the spec leaves room, none met by a real robot: `add` never sends an `id` and `update` always does; a list of no days is refused; several runs must share one `rank_id` (6.1 says so of a multi-zone request). The spec has no command for the `enabled` of the schedule as a whole and no time zone for `time`.
- A real robot answered `scheduling.show` just as 6.2 has it: `enabled` and one event, `id` `"1"`, its command with both ignored fields and one run whose `map` names a floor plan with `track_id` `null`. So an event on a floor plan is what a robot used with its maker's cloud is likely to hold.

### Settings (`commands.settings`, `Web._settings`)

- The user asked for "robot settings", then had the sounds removed "completely" (2026-10-19), from the page and, by my reading of "completely", the server. So the server sends three: `robot_language`, `cleaning_options`, `ota_updates`; `settings.sounds` and `settings.set_sounds` are refused like any other non-setting. `settings.factory_reset` is left out: it is no setting, it cannot be undone, and what a reset robot keeps of being bound to this server is not known. The robot keeps its settings and the server stores none.

A value is an object of exactly the setter's fields in the spec, all of them, also where the spec has one optional: `set_cleaning_options` would change nothing without its one field. `force_floorplan` and `auto` are booleans. A `language` is any non-empty text: the robot matches it against its `available_languages` in any case, and the server does not ask for the list first.

### Floor plans (`commands.floorplan`, `Web._floorplan`)

- The user asked for `maps.promote_floorplan`, `maps.update_floorplan` and `maps.demote_floorplan`. A floor plan is a map the robot keeps, made of what it is sent, so the server sends back a map the robot uploaded. `_floorplan` answers 404 for a map not among the robot's, 400 with what `floorplan` refuses, then `_call` with a `noted` of `save_floorplan` (promote, update) or `delete_floorplan` (demote).
- `floorplan` builds the body of 6.3 from checked values: the map's `rank_uuid`, its `map.rank_binary` and `map.real_binary` as the Base64 uploaded, and of `robot.base` only `x`, `y` and `dir`, since a robot refuses a base with a key too many and an upload may carry more. `date_created` is the map's `timing.end`, which is what a robot sends when it promotes a map by itself (7.3); the robot keeps it as the floor plan's end and names its files by it, and one it cannot read as a UTC timestamp fails the promotion, so a `timing.end` not written `YYYY-MM-DDTHH:MM:SSZ` is refused (`_ended`). A promotion goes with `nogo_track` `null` and `cleaning_tracks` `[]`, as a robot's own (7.3); an update in the reduced structure.
- Choices where the spec leaves room, none met by a real robot: `promote` never names an `old_rank_uuid` and `update` always does; a UUID must be 8-4-4-4-12 hex digits, where the spec takes any non-empty string, because a robot deletes by it; a binary must be strict Base64, which real ones are; a floor plan is not put in its own place. Nothing else is asked of a map: not that its run was complete, not that its base lies on it.
- A real robot gave `{"x":2147483647,"y":2147483647,"dir":0.0}` as the base of four maps whose `persistent_rank_uuid` was `null`, and a real position in one that had one. That number, the largest of 32 bits, is the spec's mark of a base the run never placed; it is passed on as given, being what the robot would promote the map with. The spec has a robot accept it and keep it, unverified, and says a server SHOULD promote a map with a real base where there is one; neither the server nor the page tells such a map apart. The `persistent_rank_uuid` of the fifth was the `rank_id` the robot's schedule named, which is why the page takes that field for the floor plan a run was on; the spec says only that it is a string or `null`.
- No ability lists a robot's floor plans, so `floorplans` is all the server knows. A row not written after a 200 is a 503 whose `error` says the robot accepted; asking again puts it right (the spec has a demotion answered 200 also for a floor plan that is gone). A floor plan from the maker's cloud is not in the table, which is why neither `demote` nor the `old_rank_uuid` of `update` is held to it.

### Zones and no-go lines (`commands.track`, `Web._track`)

- The user asked to "implement zones and no-go lines" with "zone editing controls on the map image view if map was promoted to floor plan". The spec calls both tracks of a floor plan (6.3): `maps.save_track` creates or replaces some, each with its `track_uuid`, its floor plan, a `type` of `cleaning` (a zone, with `track_name` and `cleaning_mode`) or `no-go` (with neither, "conventionally" `null`) and a `track_binary`; `maps.delete_track` drops some by UUID; a demotion drops a floor plan's. A floor plan has one track of no-go lines, my reading of the single `nogo_track` of a promotion, so all its lines are one track, replaced whole at each change; each zone is a track of its own. A run names a zone as its `track_id`, and `nogo_enabled` says whether it minds the lines.
- The track file (spec 6.3.1, read off the robot's loader): `track` copies the header of the floor plan's `real_binary` (origin, resolution and `alignment`) but for the maxval; the `rank_binary` must be of the same size (`_grid`); the file is a binary PGM of two bytes to a cell, little-endian, maxval 65535; a cell of the zone, or one a line goes through, is 1024 (`_MARKED`), the value the robot's zone loader takes for a cell of the zone, and every other cell 0; it is compressed with zlib and sent as Base64. The floor plan's own binaries are 8-bit and must have a maxval of 129 to 255, the only ones a robot reads a byte-per-cell file with. The first zone sent to a real robot, a rectangle of 255 in an 8-bit file, was accepted by `maps.save_track` and made a start on it fail with `pm_load_fail`: the reader's maxval check for a track's 16-bit layer takes 32769 to 65536 alone.
- `alignment` is a value the header records, not a turn of the picture: on the five stored maps with cleaned cells, with alignments of 0.24 to 1.54, 90% to 97% of the cleaned cells of the `real_binary` lie on clear floor of the `rank_binary`, so a cell drawn on the page is that cell of either.
- A robot stores a track without reading it and loads one only for a run that uses it, so a track it cannot read fails those runs alone, and deleting it puts that right (6.3.1). `_pgm` inflates no more of a binary than its header (`_HEADER_MAX`) and refuses one of more than `_CELLS_MAX` cells, the robot having chosen that header.
- A zone is any polygon (user, 2026-10-21; it was a rectangle of whole cells): 3 to `CORNERS_MAX` (100) corners, each two whole numbers that are a point where cells meet, from 0 to the map's width and height. Its cells are those it covers any part of, which `_covered` finds a row at a time, exactly, in whole numbers: no corner is within a row, only on its edges, so the sides crossing a row cross all of it in one order, and each run of the polygon across it reaches as far as its two sides do at the row's top or bottom. It must be simple (`_corners`): no corner twice, and no two sides sharing a point but the corner where one ends and the next begins, so a side may not double back on the one before; corners on one line are allowed. A robot fills a zone as one area from a floor cell inside it and fails a run on a zone with none (6.3.1); the cells a simple polygon covers are one area, joined by sides however thin it is, and a polygon that crosses or touches itself is refused, as what a robot does with several areas is not known.
- A zone kept before polygons is in `tracks` as its rectangle, the four numbers of its top-left and bottom-right cells (no migration); the page reads it as that rectangle's polygon (`polygonOf`) and it is saved as a polygon once changed.
- A line goes from cell to cell by Bresenham's, with the cell at each corner of a diagonal step marked too (`_drawn`), so nothing passes it diagonally. Cells are counted from the left and top of the `rank_binary`, as the page has them.
- Limits, mine: a zone's name is made one line as a robot's is, 1 to `ZONE_NAME_MAX` (32) characters with no control character; a floor plan has 1 to `LINES_MAX` (100) lines, none ending where it starts; and at most `ZONES_MAX` (6) zones, which `_track` holds a new zone to by the floor plan's zones in `tracks`, and a change is not held to. Six is as many as the page has zone colours (user: a fixed palette as long as the most zones there may be); the number is mine.
- `_track` answers 404 for a floor plan that is no row of the robot's `floorplans`, or whose map is gone, and for a `track_uuid` that is no zone of that floor plan in `tracks`. A new zone gets a UUID of version 4 from the server; the lines get the floor plan's own no-go track where it has one, whatever the request names. Then `_call` with a `noted` of `save_track` or `delete_tracks`. A `delete` is not held to the table, as with `demote`. `track_binary` is redacted in events.
- No ability lists a robot's tracks, so the page shows only those the server had it keep; the schedule names a zone from elsewhere by its UUID.

### Deleting a robot (`Server.delete`, `Web._delete`)

- The user asked that a robot can be deleted with all its data "from db and filesystem". The database is all this server writes of a robot; its one other file is its key under `keys`, which the operator put there. That the request covers the key is my reading, and it keeps a deleted robot away where logins are verified.
- `_delete` answers 404 for a robot without a row in `robots`, so neither the events of a robot without a page nor the key of one that never connected can be deleted through it; 200 `{}` once it is gone; 503 with an `error` when not.
- `Server.delete` goes in an order chosen for what a failure leaves. First, with `keys` set, the key file and the key in memory: a file that cannot be removed is an `OSError`, the 503, with nothing else touched, which is what a key on the read-only mount `docker-compose.yml` suggests gets; and with the key gone the robot cannot log in during the rest. Then it closes every session of the robot's and waits for their tasks, since a session writes until `run` returns, its `disconnect` last, and a row after the delete would be left over; it finds them in `_running`, kept by `_handle` from the handshake to the end of `run`, since a session a newer login replaced leaves `sessions` before it ends. Last, with nothing awaited, as no session was found, `Store.delete`. If that fails, the other 503, the key and session are gone but the rows are not, so the robot is still listed and asking again finishes. Without `keys` a deleted robot logs in again as a new one; the loop in `delete` is for one that does so while its older session is awaited.

### Binding a robot (`/api/setup`, `static/` helpers)

- The user asked for a button on the list that points a robot at this server with `reconfigureNeato`, named "Bind a robot", with the link icon, on the button and as the title of what it opens; the first paragraph under that title is the user's wording, so change it only when asked.
- The user put four browser-side helpers in `static/`: `webusb-transport.js` (WebUSB bulk transport), `mtp-client.js` (raw MTP), `mtp-fs.js` (the file system over MTP) and `neato-config.js` (`setOrbitalHosts`, `setVendorHost` and `uploadCert`, which rewrite the robot's `/etc/hosts`, `vendors.ini` and trusted certificate, and `reconfigureNeato`, which does the three in turn). The work is entirely in the browser, over USB; the server sends the robot nothing. All four are served from `_PAGES` and packaged like the other static files, `mtp-fs.js` with no special handling (user; an `_OPTIONAL_PAGES` arrangement was dropped).
- `GET /api/setup` gives the `public_address` to write into the robot's hosts file for `orbital.deorbit`, and the CA the robot must trust, which `_ca` reads afresh as `ca.crt` beside the certificate: never `ca.key`. Both are public, so it is a plain GET, not behind `_own_page`.
- `public_address` is empty by default, and then `main` detects one at startup (user) with `local_address` in `config.py`, logging what it found or warning it found nothing. An address the server listens on alone is the answer, unless it is the loopback, which no robot reaches; for `0.0.0.0` or `::` it is the address the system would send from to another network, asked for by connecting a UDP socket to 192.0.2.1, an address set aside for documentation, which sends nothing; a `host` that is a name is not looked up. It gives an IPv4 address or none, a wrong one on a machine with several networks or a VPN, and in a container with a network of its own the container's own, so the README says to set the setting with Docker Desktop. `Web` gives what `Config` holds, so the web tests see no detected address.
- `mtp-fs.js` is not in git, so a checkout or wheel may lack it. The page therefore loads the helpers with a dynamic `import()` only when the bind page opens (`loadHelpers`): the rest of the UI works without them, and the device prompt stays the first `await` of the press, which WebUSB needs for its gesture. Without `mtp-fs.js` the import fails and a toast says so.
- The flow: `WebUSBTransport.open` → `MtpClient.openSession` → `new MtpFileSystem(client)` with its `log` set to the page's → `setOrbitalHosts(fs, ip, options)`, `setVendorHost(fs, options)`, `uploadCert(fs, certBytes, options)`, one call per step rather than `reconfigureNeato`, so the page knows the step under way; a result that is not `ok` fails the run, as `reconfigureNeato` takes it. The options follow the contract `neato-config.js` documents: without an `onConfirm` every write aborts, the default declining, which is the "aborted by user" failure of 2026-10-08, so `onConfirm` approves every write, the press of Configure robot being the consent; no `onBackup` is given, so the originals are kept in memory only, for the helper to verify and restore with, and nothing is downloaded, which the README says; an aborted result is reported as aborted, not as a refused write. The `MtpFileSystem` line is built to that contract, `mtp-fs.js` being unread, and is the one line to correct if its exports differ.
- The certificate is installed on every robot (user), with nothing to tick; a server with no `ca.crt` skips the third step, says so, and the run goes on.

### Home Assistant (`mqtt.py`)

- The user asked for Home Assistant over MQTT and chose aiomqtt, a third dependency where the HTTP side is hand-written; and, for a first version, the vacuum, its sensors, the zones as rooms and the alerts as events, not the map's picture or the settings.
- `_serve` makes an `Mqtt` where `mqtt_host` is set, before `Web`, which gets it; `Server` knows nothing of it. It takes the `Store` and `Server.sessions`. It keeps one broker connection in a task of its own (`_run`), retried every `_RETRY` seconds while the broker is out of reach and after a connection ends, and logs why once until the reason changes. Nothing of it ends the server: an unforeseen exception is logged and the connection tried again.
- Publishing is made from the database. `Store.watch` calls `_changed` with a robot after each write of it, and `_update` makes each retained message as it now is (`_wanted`) and publishes only those that differ from what the broker holds (`_sent`), so a heartbeat publishes nothing. A robot is published once it has a row in `robots`; a deleted one has its retained messages cleared with empty ones. At each connection and when Home Assistant says it started (`online` on `<prefix>/status`), every robot is published again with `_sent` taken as unknown (`None`), since a broker may lose what it retains; a robot announced before and deleted since is cleared then. One deleted while the server was down is not, which is a gap.
- Topics under `mqtt_topic` (`deorbit`): `status`, `online`, or `offline` as the server stops and as its last will; per robot under its `_node` (vendor and serial joined by `_`, any character but a lowercase letter or digit made `_`, a hash of the two after them so that two robots cannot come to one): `availability` (`online` while it has a session), `vacuum` (`state`, `fan_speed` and `segments`, as Home Assistant's MQTT vacuum reads them), `state` (`battery`, `charging`, `docked`, `errors`, `connected`, read by the sensors' templates), and the unretained `alert` and `notification`. Home Assistant publishes to `command`, `fan_speed` and `clean_segments`. Retained messages and events go at QoS 1.
- A robot is one device of device discovery at `<prefix>/device/deorbit_<node>/config`: the vacuum, named as the device, with start, pause, stop, return_home, locate and fan_speed (not `status`, which only gave a text); the sensors Battery, Charging, Docked, Errors and Connected; the events Alert and Notification. Every entity needs this server and the robot (`availability_mode: all`), but Connected only the server. The device is named as the web UI calls the robot; its manufacturer is Neato for vendor `n` and Vorwerk for `1` and `2`, by the cloud hosts of spec section 2, and none for another; its software version is the firmware of its last connection since the server started.
- The vacuum's `activity`: `error` and `paused` for those states; `cleaning` for busy cleaning or `cleaning_standby`; `returning` for busy docking; otherwise `docked` or `idle` by `is_docked`. Errors is the codes of the robot's errors, or `none`, cut to Home Assistant's 255 characters; a charge that is not finite is `null`, which the template writes as `None`, unknown.
- `start` resumes a robot whose last state says it can resume, which is Home Assistant's start on a paused vacuum, and otherwise starts on no floor plan in the fan speed's mode with `normal` navigation; the fan speed is `eco` until set and kept in memory, so a restart resets it. `stop` is a cancel, `locate` a Find me. Each goes through `Session.call` in a task of its own (`_calls`), which logs how it went with Home Assistant as who asked; a robot not connected is logged here. A command the broker retained is ignored, as it would run again at every connection.
- Segments are the zones of the floor plans in `floorplans`, by `track_uuid`, under the zone's name, with the floor plan's name in brackets where the robot has zones of several: what its map is called, or when its run began, written as the web UI writes it but in the `timezone` setting's zone. Home Assistant has the user map them to areas and asks again when they change. A `clean_segments` sends one `cleaning.start` with a run per zone, in the order given and each once (`commands.cleaning`, checked as a schedule event's runs): each in its own mode, `normal` navigation, minding the no-go lines where the server had the robot keep some. Refused with a warning: segments that are not a list of strings, a zone not in `tracks`, zones of several floor plans (6.1), and a robot whose last state says it is not docked.
- Alerts and notifications are read from the event log (`_tell`, `Store.alerts`) after the last event looked at, which is `Store.last_event` at each connection, so nothing from before or from while disconnected is told. A `robots.error_codes` is an Alert event of its severity, `warning`, `error` or `critical`, with its `code`, and one of another severity is not told; a `robots.notify` is a Notification whose type is its `message_code` where spec 7.1 lists it and `other` otherwise, an entity's event types having to be listed in advance, with its `code` and `payload`.
- `Mqtt.status` gives `connected`, set by `_connected` where it logs the connection and cleared by `_run` as it ends, and `error`, `_failure`: why the last try failed, the log's text, `None` before a failure and after a success; an unforeseen exception gives a text pointing to the log. That is the server's connection to the broker, all it knows: Home Assistant's birth and will on `<prefix>/status` are not retained by default.
- On Python 3.11 `asyncio.wait_for`, which aiomqtt waits for the broker with, can let a cancellation go by when its result comes at the same time, and the task goes on; a `TaskGroup` then waits for good, which hung a test's cleanup one time in two and would hang a stopping server. So `_connected` runs publishing and receiving as two tasks and waits for either to end, `_end` cancels a task again every `_END_AGAIN` seconds until it has ended, and `stop` gives the client `_STOP_TIMEOUT` to say goodbye first.

## Web page (`static/`)

### Conventions

- Plain JavaScript that polls the API. A view is redrawn whole when its data changes, so anything a redraw must not undo is kept on the view object (opened rows, the tab shown, drafts). The view keeps the server's last answer (`body`) so `drawRobot` can redraw when only view state changed, and `refresh` drops a poll sent before a change.
- A table the page looks a robot-chosen name up in, such as `SERVICES`, is a `Map`: on a plain object a service named `constructor` would find something.
- Everything a robot sent reaches the DOM as text nodes. The `Content-Security-Policy` forbids inline script and style, so `index.html` has neither, nor `style` attributes; set styles through `element.style`. `img-src 'self'` keeps `data:` images out.
- `draw` leaves the page as it is while text is selected (`selecting`), an `input` or `select` has focus (`entering`), or a map is dragged (`dragging`), since a new page would take the canvas out of the document. So a handler whose press has to show clears the selection and moves focus to a button before it draws, and `draw` asks which element has focus before it builds. The bind page is the exception.
- A button held back uses `aria-disabled`, not `disabled`, which would drop the keyboard's focus, with the reason in its `title`. `robotButton` is the button that asks something of a connected robot, shared by the schedule, settings, floor plans and zones, with an icon when given a `glyph`, `alone` on a row.
- What must match the server, each checked by a test: `COMMANDS`, `COMMAND_TIMEOUT_MS` (longer than `_COMMAND_TIMEOUT`), `EVENTS_MAX`, `MAPS_MAX`, `NAME_MAX`, `DAYS`, `MODES`, `NAVIGATION_MODES`, `SETTINGS` (in order) and `ZONES_MAX`.
- The page asks for 25 events and 10 maps, and that many more each time older ones are shown (`asked`).

### Maps (`map.js`, `viewer`)

- The server decodes nothing: the page fetches a map with `/api/map` when its row first opens and draws it on a canvas. `map.js` reads and paints and touches no document, so it runs under Node; `app.js` imports it, so `_PAGES` must serve it.
- The spec says of a binary only that it is a "compressed PGM"; the rest is read off what a real robot (1.7.0) uploaded, not its software. zlib data inflating to a binary PGM (`P5`) of 2000 by 2000 one-byte cells, whose header ends in a single `\r` and carries `# Neato metadata: origin_x=-40000 origin_y=-40000 resolution=40 alignment=0.000000`, in millimetres: the corner the picture starts from, also the JSON's `origin`, and the side of a cell, so a file covers 80 m by 80 m with 0, 0 in the middle. The `alignment` is, per 6.3.1, a turn in radians a floor plan's training found to straighten the map; a `rank_binary` may have one, a `real_binary` has 0; the picture is not turned by it (see "Zones and no-go lines"), so the page ignores it. The first row is the far end of the y axis, settled by the cleaned cells against the robot's `pos`.
- In `rank_binary` 128 is a cell not looked at, 0 clear floor, 255 a wall, with every value between. In `real_binary` 3 and 4 are cleaned cells (59 of them at 40 mm made that run's `stats.area` of 0.0944, so square metres), 6 fills a square of 256 cells around where the robot has been, and 0 the rest; what tells 3 from 4 is unknown, and the page names any other value under the picture. `robot.pos` and `base` are in the same millimetres; a `dir` is degrees anticlockwise from the x axis, 274 while driving towards lower y. Both samples were runs of under a minute, so longer runs may hold values not seen yet.
- `readBinary` stops inflating at `INFLATED_MAX` and `paint` refuses more than `PIXELS_MAX`, a robot choosing those bytes. `paint` makes a pixel per cell, cut to what the robot saw, and says where it starts among the cells (`left`, `top`).
- `viewer` (user: one window size and shape with Zoom in, Zoom out and dragging): 4:3, half the width of its row or floor plan block, on the Maps tab and in the schedule's form alike (user), the whole width on a narrow screen. A canvas of its size in screen pixels is drawn anew from the picture at each change, so the marks of the robot and base keep their size. A map starts whole and centred, a small one enlarged at most `FIT_MOST`. Zoom doubles or halves a cell about the middle, rounded to whole screen pixels, from whole to `CELL_MOST`; the button at its end is `aria-disabled`. Below two screen pixels to a cell the picture is smoothed, so a wall of one cell stays, and above that sharp. Move the map, with arrows (`aria-pressed`), is pressed at first on every picture (user); while pressed and the map is larger than the window the pointer drags it, captured; let go, a drag does nothing but draw, while a zone or lines are drawn. The canvas is a Tab stop, whose arrow keys move it by `PAN_STEP` either way; nothing goes past the edge. No wheel or pinch zoom, so the wheel scrolls the page; a finger drags only while the map is movable (`touch-action`). Colours are in `PALETTES`, since a canvas cannot read the stylesheet; the whole canvas is painted, ground included.
- The view keeps each picture in `drawings` by map `id`: its node, `repaint`, and the zone it shows as chosen. A redraw moves these nodes into the new page, so a map is fetched and inflated once and keeps its zoom and pan, and `drawRobot` repaints each, for what is drawn over it. A node is in one place, so a picture shown elsewhere, the schedule's form, is kept per place (the `place` of `drawing`) and fetched once per form. Each poll lets go of the pictures of maps no longer listed (`forgetMaps`), since a deleted map's `id` may come back on a later one.
- A map's row (user): Name, or the start time where it has none; Status, its run's state as given, the number of runs for several and a dash for none; Area, what its runs cleaned; Duration, from start to end. Start time is `timing.start`, not the arrival, so a run's maps share it. A map that is a floor plan has no row. Opened (user): Start time, End time, Paused for, Started by, Cleaning complete, Mode and Navigation (`mapFacts`, one value where runs agree, `setting`), and the picture to their right, under them on a narrow screen; no line for `rank_uuid` or `persistent_rank_uuid`. A map of several runs also has a line per run with its state and area. The Other maps panel has no explanation (user).
- **Map names** (user: "make it possible to name maps"; Name in place of Start time in the table, Start time in the opened row, a rename button in the row with its form in a popover, and a map called by its name in "all ui elements that refer to the particular map", by default its start time): `mapText` is the name or the start as `numeric` writes it, `mapShown` the name or the start as `dated` shows it. A map is so called in its row, in a floor plan's heading, as the floor plan of a schedule event (row, form, choices) and of the Start menu (`floorText`, `floorShown`, `placeOf`), in the questions of Demote and Replace, in the toast of a rename, and in the Details of an upload event, by `map_names` for its `rank_uuid` or else the upload's start. A floor plan whose map the server does not know is named by its `rank_uuid`. Rename is a pencil, the first icon of a row (`mapTools`), and a labelled button before Demote in a floor plan's block, one `data-focus` in both (`map-name-<id>`), so focus follows a map that is promoted or demoted. It needs no connection.

- **Deleting a map** (user: "would it be possible to implement map delete?"): Delete, a trash icon, last in a map's row (`dropMapButton`), asks in a popover (`askDropMap`), Keep or Delete it, that it goes from this server with its name and that the robot is sent nothing. The button is held while the view's `mapDeleting` waits and while `floors` does, a Promote or Replace of that map being possibly under way. It needs no connection. ## Protocol constraints that are easy to break

These come from the spec and are not all enforced by tests:

- The server must never send an `event` to the robot — only `request` and `response`. An event makes the robot drop the connection.
- `robots.notify` arrives as a `request` but must not be answered. `peer.state` and `robots.error_codes` are events and are not answered either.
- A frame's header and payload must go out in one write (`encode_frame` returns them joined), and writes on a connection must not interleave (`Session._send` holds a lock).
- The robot disconnects after 70 seconds without a frame, and its own requests time out after 30 seconds, so handlers must reply promptly. If a handler ever needs to do slow I/O, it can no longer run inline in the receive loop.
- The login response has no `type` or `id`; a non-200 `code` makes the robot disconnect and retry.

## HTTP API

What `web.py` answers besides the files of `static/`, all JSON. The page is its first user; the README does not mention it.

| `GET` | Content |
| --- | --- |
| `/api/robots` | every robot without its `state_json`, by vendor and serial |
| `/api/robot?vendor=V&serial=S` | `robot`, with `state_json`; its latest 25 `events` and 10 `maps`, newest first, or `events=N` (up to 1000) and `maps=N` (up to 100), with `more` and `more_maps` for whether there are older ones; all its `floorplans`, the last accepted first; `floorplan_maps`, the older maps those were made of, newest first, empty when `more_maps` is false; the `tracks` of its floor plans; `map_names`, the `rank_uuid` and `name` of each named map, oldest first; or 404 |
| `/api/map?vendor=V&serial=S&id=N` | one map of that robot as `map`, whole, or 404 |
| `/api/setup` | `address`, the `public_address` as set or found at startup, empty for none, and `ca`, the text of `ca.crt` or `null` |

`/api/robots` and `/api/robot` also give `now`, the server's time; `version`, the page's 16 hex digits; and `home_assistant`, `null` without `mqtt_host`, else `connected` (true or false) and `error`, why the last try failed or `null`.

A robot is its `robots` columns as stored, its `name` or `null`, the fields below, and a `session`: `null`, or the `address`, `firmware` and `since` of its connection (earlier ones are in its login events). True and false are 1 and 0, objects and arrays JSON text, and a field the state lacks `null`; an idle robot sends no autonomy states. An event is its `events` columns; a map its `maps` columns and `name`, its `map_json` without the two binaries except from `/api/map`.

| Field | Where in the state |
| --- | --- |
| `state`, `action`, `errors` | the fields of those names; `errors` is `null` when it reports none |
| `can_start`, `can_cancel`, `can_pause`, `can_resume`, `can_return_to_base` | `available_commands` |
| `is_charging`, `is_docked`, `charge`, `base_type`, `is_quickboost`, `quickboost_estimate` | `details`; `charge` is a percentage |
| `base_error`, `bag_status`, `is_extracting` | `cleaning_center` |
| `autonomy_states` | `autonomy_states`, whole |
| `autonomy_started_on_base` | its `started_on_base` |
| `autonomy_cleaning_start`, `autonomy_undocking`, `autonomy_active_cleaning_session`, `autonomy_docking_for_suspended`, `autonomy_docking_successful_suspended`, `autonomy_suspended_charging_start`, `autonomy_undocking_after_suspended`, `autonomy_active_cleaning_after_suspended`, `autonomy_docking`, `autonomy_docking_verify_base`, `autonomy_docking_successful` | its other fields: when the robot reached each step, in seconds since 1970 by its clock, or -1 for one not reached |

Every `POST` names the robot as `vendor=V&serial=S`, has no body and needs the `Origin` a browser adds, naming the host it is sent to:

```sh
curl -X POST -H 'Origin: http://localhost:8080' 'http://localhost:8080/api/command?vendor=n&serial=SERIAL&command=pause'
curl -X POST -G -H 'Origin: http://localhost:8080' 'http://localhost:8080/api/track?vendor=n&serial=SERIAL&action=zone&rank_uuid=414fb561-91a7-4a95-8fc7-200169d2d5af' \
  --data-urlencode 'zone={"name":"Kitchen","cleaning_mode":"eco","polygon":[[980,1010],[1061,1010],[1061,1040],[1020,1040],[1020,1076],[980,1076]]}'
```

| `POST` | Parameters | Invokes |
| --- | --- | --- |
| `/api/command` | `command`: `start`, `pause`, `resume`, `cancel`, `return_to_base` or `find_me`; a start may add `run=JSON` | the ability of `COMMANDS` |
| `/api/schedule` | `action=show`; `add` with `event=JSON` without an `id`; `update` with `event` with the `id` it replaces; `delete` with `id=N` | `scheduling.*` |
| `/api/settings` | `action=robot_language`, `cleaning_options` or `ota_updates` to read; `set_` and the name with `value=JSON` to change | `settings.*` |
| `/api/floorplan` | `action=promote` with `map=N`; `update` with `map=N` and `old_rank_uuid=U`; `demote` with `rank_uuid=U` | `maps.promote_floorplan`, `maps.update_floorplan`, `maps.demote_floorplan` |
| `/api/track` | `action=zone` with `rank_uuid=U`, `zone=JSON` and to change one `track_uuid=T`; `nogo` with `rank_uuid=U` and `lines=JSON`; `delete` with `track_uuid=T` | `maps.save_track`, `maps.delete_track` |
| `/api/name` | `name=NAME` | nothing: names the robot |
| `/api/map_name` | `id=N`, `name=NAME` | nothing: names the map |
| `/api/map_delete` | `id=N` | nothing: deletes the map and its name |
| `/api/delete` | nothing more | deletes the robot |

The five that call a robot answer 200 when it answers, with the `ability` and the robot's `code` and `body`, and for a command `sent`, the server's time as it went, which a later `state_at` is after; a `code` of 200 is the robot accepting. Otherwise an `error`, with 400 for a request the server does not take, naming what is wrong; 403 from another site; 409 for a robot not connected; 504 for none in 10 seconds; 502 for a connection that ended first. `/api/floorplan` and `/api/track` add 404 for a map, floor plan or zone that is not in the database and 503 when the robot accepted and the database was not written, after which the request can be sent again. `/api/name` and `/api/map_name` answer 200 with the `name` as kept, `null` when there is none left or none given; 400 for more than 64 characters or a control character; 404 for a robot or map of the robot that is not in the database; 503 when it was not written. `/api/map_delete` answers 200 with `{}` once the map is gone, 404 for one that is no map of the robot's in the database, 409 for one a floor plan was made of or is being made of, and 503 when it is still there. `/api/delete` answers 200 with `{}` once the robot is gone, 404 for one not in the database, and 503, when it is still listed and the request can be sent again.

- A run is `settings`, a `mode` of `eco`, `turbo`, `auto` or `max` and a `navigation_mode` of `normal` or `gentle`, and a `map` that is `null` for no floor plan or has the `rank_id` of one, a `track_id` that is `null` for the whole of it or a zone, and `nogo_enabled`. A start without a `run` is on no floor plan in `eco` with `normal`. A robot answers a start on a floor plan or zone it does not have with a `code` of 422.
- An event is `enabled`, true or false; `days`, one or more of `mon` to `sun`; `time`, `00:00` to `23:59`; and a `command` whose `ability` is `cleaning.start` with one or more `runs`, all of one floor plan; an `id` is a string of digits. The robot gives an added event its `id`, which only `show` tells. The schedule's own `enabled` cannot be changed, so the page mentions it only when it is off.
- A setting reads as a `body` of `language`, `available_languages` and from some robots `gender`; of `force_floorplan`; or of `auto`; and is changed by `{"language": L}`, `L` among the `available_languages`, `{"force_floorplan": B}` or `{"auto": B}`. A change is answered with an empty `body`, so it is read again to be seen. A factory reset and the sounds cannot be asked for.
- A floor plan's map must have a `timing.end` written `YYYY-MM-DDTHH:MM:SSZ`. `U` must be a UUID but need not be in `floorplans`: one from elsewhere, such as a map's `persistent_rank_uuid` or a `rank_id` in the schedule, is named the same way. Only on a 200 do `floorplans` and `tracks` change.
- A zone and lines are in cells of the floor plan map's `rank_binary`, from 0 at its left and top. A `polygon` is 3 to 100 simple corners `[x, y]` where cells meet, the zone being every cell it covers any part of, so the rectangle of cells `[x0, y0]` to `[x1, y1]` is `[[x0, y0], [x1 + 1, y0], [x1 + 1, y1 + 1], [x0, y1 + 1]]`; a `name` is 1 to 32 characters; `lines` are 1 to 100 of `[x0, y0, x1, y1]`. A new zone past 6 is a 400. The rest is under "Zones and no-go lines". `T` need not be in `tracks` for a `delete`.

## Database

The `database` file is created with its directory at the first start. Times are UTC, written like `2026-10-08T13:55:37.511Z`.

| Table | Columns |
| --- | --- |
| `robots` | `vendor`, `serial`: the robot, both lowercase, as the log names it, `[<vendor>/<board serial>]`; `heartbeat_at`, its last heartbeat, one a minute; `state_at` and `state_json`, its last state, whole, replacing the one before, empty before one came |
| `names` | `vendor`, `serial`, `name`: a robot given a name |
| `map_names` | `vendor`, `serial`, `map_id` (its `id` in `maps`), `name`: a map given a name |
| `events` | `id`, the order recorded; `at`; `vendor`, `serial`; `kind`, `login`, `disconnect`, `call` for an ability the server called, or the type of the robot's message, `request`, `event` or `response` for its answer to a call; `service`, of a request or event, else empty; `body_json`, the message's body, empty for none; for a login its `address`, `firmware` and whether its signature was `verified`; for a disconnect the `reason`; for a call what was sent, naming the `ability`; for a response that `ability` and the robot's `code` and `body` |
| `maps` | `id`, the order of arrival; `at`; `vendor`, `serial`; `map_json`, the `maps.create` body whole, with `map.rank_binary` and `map.real_binary`, each a compressed PGM as Base64. A `maps.create` with the `rank_uuid` of a map the robot already has adds no row. A map deleted from the web UI goes with its name, and its `id` may be given to the next map |
| `floorplans` | `vendor`, `serial`; `rank_uuid`, what the robot knows it by, the `rank_uuid` of its map; `map_id`; `at`, when the robot accepted it. One row per `rank_uuid`; only what this server gave |
| `tracks` | `vendor`, `serial`; `track_uuid`; `rank_uuid`, its floor plan; `type`, `cleaning` for a zone or `no-go`; `name`, `mode`, `NULL` for no-go lines; `shape_json`, in cells of the floor plan's `rank_binary` from its left and top: a zone's corners `[[x, y], ...]`, or for one kept before polygons its rectangle `[left, top, right, bottom]`, or the lines `[[x, y, x, y], ...]`; `at` |

Signatures and binaries in events are replaced by their length, like `<2048 chars>`. A state, map or body not stored because SQLite could not read it back as JSON has a number such as `1e999`, too large to read, or text that is not Unicode. The file can be asked while the server runs; `->>` needs SQLite 3.38 or later, where `json_extract(state_json, '$.state')` reads the same, and true and false come out as 1 and 0:

```sh
sqlite3 data/deorbit.db "SELECT serial, state_json ->> '$.state', state_json ->> '$.details.charge', state_at FROM robots"
sqlite3 data/deorbit.db "DELETE FROM events WHERE at < date('now', '-30 days')"   # nothing prunes the events
sqlite3 data/deorbit.db "SELECT map_json ->> '$.map.rank_binary' FROM maps WHERE id = 1" | base64 -d | python3 -c "import sys, zlib; sys.stdout.buffer.write(zlib.decompress(sys.stdin.buffer.read()))" > rank.pgm
```

## Tests

- `tests/test_server.py` is end-to-end: a scripted `Robot` talks to a real `Server` over TLS on an ephemeral port, with certificates and a robot key generated once per test class. `ServerTestCase.start(**overrides)` takes `Config` overrides, which is how tests shorten `heartbeat_interval`, `idle_timeout` and the like. `login()` returns the wire-side `Robot` and the server-side `Session`, so a test can drive either end. Each test has its own database file, named after it, in the class's temporary directory. `DeleteTests` there is `Server.delete` itself; `ConsoleTests` the console, through `assertLogs`, which sets the level it captures from.
- `tests/test_config.py` covers the settings file. Its command-line cases call `main()` through a helper that patches out `_serve` and `logging.basicConfig`, keeping the latter's mock as `console`, so no server starts and no console handler outlives the test, and puts a mock in place of `local_address`, which finds nothing unless a test says so; a case that generates a certificate does so in its temporary directory. `LocalAddressTests` is the function itself, with a mocked socket in all but one test.
- `tests/test_store.py` drives a `Store` directly and checks the file through a second connection.
- `tests/test_web.py` starts a `Web` beside the `Server` of `ServerTestCase` and speaks HTTP to it over a raw connection, so it can send malformed requests and choose the `Host` and `Origin`; `api()` fails on JSON a browser would refuse. `CommandTests`, `ScheduleTests` (whose long test lists everything `scheduling` refuses, with its `error`), `SettingsTests`, `FloorplanTests` (a map stored for each thing `floorplan` refuses) and `TrackTests` (a floor plan of 20 by 10 cells, each binary sent read back as rows) have the scripted robot answer, and rely on in-order handling to show that a refused request sent the robot nothing. `NameTests`, `MapNameTests` and `MapDeleteTests` make a file that takes no write with a trigger through a second connection. `DeleteTests` starts its server on `registry()`, a copy of the class's key directory, the class's own being shared; a key file that cannot be removed is a patched `Path.unlink`. `VersionTests` is the page's version; `ServeTests` runs `_serve`.
- `tests/test_mqtt.py` starts an `Mqtt` beside the `Server`, connected to a `Broker` of the test's own: MQTT 3.1.1 as far as aiomqtt uses it (a login and a last will, QoS 0 and 1, retained messages, wildcard subscriptions, pings), keeping every message it is given, able to send one as Home Assistant would and to drop every connection, so no Mosquitto is needed. `RobotTestCase` has the scripted robot connected; a test that deletes it uses `registry()`. `HomeAssistantTests` of the web gives `Web` a mock `Mqtt`, and `ServeTests` here has `_serve` give the web UI the real one.
- The page's script has no automated tests; it is checked in a browser against a database with robots in several states. `map.js` runs under Node, where `readBinary` and `paint` take a binary from the `maps` table and give its pixels, which is how they were checked against real maps.
