## Clean-room rule

This is a clean-room reimplementation of the server that Neato robot vacuums connect to (the "Orbital" protocol). The **only** permitted source of protocol knowledge is the specification at `docs/ORBITAL_API_SERVER_SPEC.md`. Do not read, grep or list the robot's own client software, or anything that comes with it, wherever a copy is — looking at it would contaminate the clean room. When the spec is silent or ambiguous, choose a conservative behaviour and say so, or ask.

## Do not read `mtp-fs.js`

Under no circumstances read the contents of a file named `mtp-fs.js`, wherever it is. That means no read, `cat`, `grep` or any other tool on it, and none through a subagent, whose prompt has to carry this rule. A search over a directory that may hold it must exclude it by name, since a match would print its lines. Seeing its name in a listing, or asserting on the length of an HTTP response that carries it, is not reading its contents. The user gave this rule (2026-10-08) without a reason and has not lifted it. The file is in `deorbit/static/`, where the user put it; if a task seems to need what is in it, say what is missing and leave the file unread.

Distributing it is allowed, by the user's decision (2026-10-08): the web UI serves it from `_PAGES` like any other file in `static/`, and a built wheel or Docker image carries it when it is on disk at build time — `static/*` in `pyproject.toml` packages it and nothing excludes it. ## Commands

```sh
pip install -e .                 # dependencies are `aiomqtt`, `cryptography` and `PyYAML`; Python 3.11+
python -m unittest               # all tests (stdlib unittest, no pytest)
python -m unittest tests.test_server.LoginTests.test_login_response   # one test
python -X dev -m unittest        # also surfaces asyncio debug warnings and unclosed resources
python -m deorbit.certs [HOST ...]   # dev CA + server cert into certs/ (gitignored)
python -m deorbit [-c FILE]      # run the server; settings come from FILE, default ./deorbit.yml
docker compose up --build        # the same in a container, as the README has it
docker compose run --rm deorbit python -m deorbit.certs [HOST ...]
```

`python -m deorbit.certs` with hosts keeps the CA that is in `certs/` and reissues only the server certificate, for names other than `orbital.deorbit`, such as the production hostname a stock robot uses. A robot that rejects the certificate shows up on the console as a `TLS handshake failed` line.

The web UI is then at `http://localhost:8080`. It has no build step, and its files are read once at startup, so restart the server to see an edit to `deorbit/static/`, which a page that is open then offers to reload.

There is no linter or formatter configured.

When smoke-testing the real server from a script, stop it with `kill` (SIGTERM). A process started with `&` from a non-interactive shell has SIGINT ignored, so `kill -INT` silently does nothing and the script hangs.

## Current scope

The server handles the whole wire protocol and prints every message to the console. What is persisted, in SQLite, is each robot's last `peer.state` body, the time of its last heartbeat, the body of every `maps.create` it sent, the floor plans it accepted from this server with the zones and no-go lines it accepted for them, and an event log: its logins, its disconnects, the abilities the server called on it and every message it sent other than a state. Every other handler in `services.py` returns the minimal reply that keeps a robot happy (`firmware.check` → 404 "no update", `logs.list_files` → no URLs), and a map that is stored is still answered `floorplan: false`. It has been exercised only against the scripted robot in the tests, never a real one. A web UI shows the robots, their events and their maps as pictures, and which robots are connected, and sends a connected robot one of six commands (start, pause, resume, cancel, return to base, and find me, which has it make the sound it is found by), a start in the mode and navigation mode it is given, on no floor plan or on one this server had the robot keep, the whole of it or one of its zones. It also reads a connected robot's schedule and adds, changes and deletes its events, each on no floor plan or on one this server had the robot keep, the whole of it or one of its zones, reads and changes its settings (its language, whether it forces its floor plan and whether it updates its software by itself), and gives a robot a name, and a map one, which only this server knows. It has a connected robot keep a map it uploaded as a floor plan, new or in place of another, and drop one, and keep and drop the zones and the no-go lines drawn on such a floor plan's picture. It deletes a robot as well: its rows in the database, its key file and its session. It has no authentication. It also puts the robots in Home Assistant through an MQTT broker, by MQTT discovery: each a vacuum that Home Assistant starts, pauses, stops, sends to its base and has play its sound, in the mode its fan speed gives, with its battery, whether it is charging, docked and connected and its errors as sensors, its alerts and notifications as events, and the zones of its floor plans as rooms Home Assistant cleans, and the web UI shows whether it is connected to the broker. No Home Assistant has met it yet: only the tests' broker, and a Mosquitto that it published a copy of the database to. A real robot (firmware 1.7.0) has accepted start, pause, resume, cancel and return to base, and a start with a run chosen in the menu of the Start button; `utilities.find_me` has not been sent to one. It has also answered `scheduling.show` and accepted `scheduling.update`; `scheduling.add` and `scheduling.delete` have not been sent to one. It has accepted `maps.promote_floorplan` and `maps.save_track`, and then acknowledged a start on the zone it was given and raised `pm_load_fail`, not able to load it: that zone was an 8-bit file of maxval 255, which fails the robot's 16-bit track reader (see "Zones and no-go lines"). No zone or no-go lines drawn as they now are have been sent to one, and neither have `maps.update_floorplan`, `maps.demote_floorplan` and `maps.delete_track`. It has answered `settings.robot_language`, `settings.cleaning_options` and `settings.ota_updates`, and failed `settings.sounds`, which the server no longer sends, with a 503; of the three that change a setting it has accepted `settings.set_ota_updates`, and the other two have not been sent to one. No real robot has been deleted while it was connected, so what one does when its connection is ended that way is not known.

## Architecture

| Module | Role |
| --- | --- |
| `config.py` | settings, their defaults, and the YAML file they are read from |
| `framing.py` | 4-byte length prefix, heartbeat and close control frames |
| `auth.py` | robot registry, signature, clock-skew and replay checks |
| `session.py` | one connection: login, heartbeats, routing, `Session.call()` for robot abilities |
| `services.py` | replies to robot-originated services |
| `store.py` | SQLite database of each robot's last state, heartbeat time, events, maps and their names, floor plans with their zones and no-go lines, and name |
| `server.py` | TLS listener, one live session per robot, and the deleting of a robot |
| `commands.py` | the commands the web UI sends and the ability each invokes, the check of an event of a schedule and of a setting, what a floor plan is made of, and how a zone or no-go lines are drawn for one |
| `mqtt.py` | Home Assistant: the client of an MQTT broker that announces each robot by MQTT discovery, publishes its state, alerts and notifications, and sends it what Home Assistant asks |
| `web.py` | HTTP listener for the web UI, its JSON, its commands, the schedule, the settings, the floor plans and their zones and no-go lines, the names of robots and maps and the request to delete a robot |
| `static/` | the web UI itself: one page, its stylesheet and its script, of which `map.js` reads a map's binaries, `theme.js`, which sets the colour scheme, and the four helpers that bind a robot over USB |
| `certs.py` | development certificate generator |

The robot-facing protocol is not HTTP. It is a persistent TLS connection carrying frames of a 4-byte big-endian length plus a payload, where the payload is a JSON object or a one-byte control value (`0x06` heartbeat, `0x00` graceful close).

**Connection path.** `Server.serve_forever` accepts raw sockets and `Server._handle` performs the TLS handshake itself through `loop.connect_accepted_socket`, then builds the stream reader/writer by hand. This is deliberate: `asyncio.start_server(ssl=...)` swallows handshake failures, and a robot rejecting the certificate is the most likely first problem, so it must reach the log. Each connection then runs `Session.run` in its own task; `Server.stop` cancels those tasks.

**Session lifecycle** (`session.py`). `run` is the single place that maps every way a connection can end to a logged disconnect reason; internal code ends a session by raising `Disconnect(reason)`. The sequence is login → `Server.register` → heartbeat task → receive loop. `Server.sessions` holds at most one live session per robot; a newer login replaces the older one via `Session.close`, which aborts the transport.

**Event log.** `Session` is the only writer: `_login` adds a `login`, `run` adds the `disconnect` with the same reason it logs, and `_on_service` adds every message before its handler runs, except those for the services in `_UNLOGGED` (`peer.state`, since the `robots` table holds the latest state). `call` adds a `call` as it sends one, and `_on_response` adds the `response` to it together with the ability, which a response does not name; that is why `_pending` keeps the ability. A call that got no answer is thus a `call` alone, and a response that no call waits for is not logged. A body goes through `_redact` whatever `full` is set to. A rejected login leaves `Session.robot` unset, which is what keeps it and its disconnect out of the log, so every `login` in the table is one that was accepted.

**Two message directions, correlated separately.**

- Robot → server: `_on_service` looks `to.service` up in the `SERVICES` table. A handler is called with `(store, robot, body)` and returns `(code, body)`, or `None` for no reply. A reply is sent only when the envelope type is `request`. These are answered inline, in arrival order, so there is no pending-request map for this direction — which is also why a robot reusing one request ID across a log-upload job just works. Tests rely on the in-order handling to assert that a service got *no* reply.
- Server → robot: `Session.call(ability, params)` sends a request and awaits a future stored in `_pending` by ID. Responses may arrive in any order; pending calls fail with `ConnectionError` when the session closes. Its one caller outside the tests is the web UI's command endpoint.

**Identity and auth** (`auth.py`). A robot is identified by `RobotId(vendor, board serial)`, both lowercased, matching the string the robot signs. `Authenticator(keys=None, ...)` accepts every well-formed login without verification; with a key registry it checks the RSA signature, then clock skew and replay. Keys are loaded once at startup into a dict, so no filesystem path is ever built from a serial sent over the wire. `delete_key` keeps to that: it lists the directory as `load_keys` does (`_key_files`) and removes the files whose names come to the robot's, which may be several where names differ only in case. `Authenticator.forget` takes the key out of the dict, so a deleted robot is refused without a restart.

**Storage** (`store.py`). `Server` opens one `Store`, a single SQLite connection to the `database` file, and closes it in `stop`. The `robots` table has one row per `RobotId`, upserted by `save_state` (from the `peer.state` handler, which skips a body that is not an object) and `save_heartbeat` (from the receive loop). `save_state` keeps the whole body in `state_json`, as the JSON object the robot sent, and nothing else of it: no field of a state has a column, which is also how the spec's rule that unknown fields be preserved is met. `robots()` and `robot()` read the fields the web UI shows out of it with `json_extract`, each under the name `_STATE_FIELDS` gives it, and with them the robot's `name`, which `_ROBOTS` joins on from the `names` table. That table of names and JSON paths drives only those two SELECTs and nothing of it is in the file, so a new field is one line there, and one in the table of fields under "HTTP API" below. The spec names only the top-level state fields, so the nested ones in `_STATE_FIELDS` come from what a real robot (firmware 1.7.0) sent to this server, as printed on its console, not from the robot's own software. That the numbers in `autonomy_states` (`_AUTONOMY_STATES`) are Unix seconds, with -1 for a step not reached, is likewise read off what the robot sent (its `cleaning_start` equalled the start time in the `maps.create` of the same run); the spec does not mention them. They are given as sent, and only the page reads them as times. SQLite has no JSON type, so `state_json`, the events' `body_json` and the maps' `map_json` each carry a `CHECK (json_valid(...))`: a text the JSON functions cannot read would fail every read that touches its row, so it is refused at the write, where it costs one state. That is what turns away a non-finite number, which Python writes as the bare word `Infinity`. `_json` leaves text unescaped (`ensure_ascii=False`) for the same reason: a lone surrogate then fails to be bound, where as a `\ud800` escape it would pass `json_valid` and make `json_extract` return text that Python cannot decode. A whole number beyond SQLite's range is valid JSON and is stored as sent; `json_extract` reads it as a float, an infinity if it is long enough, which is why `web.py` has `_finite`. There is no migration code, by decision: `CREATE TABLE IF NOT EXISTS` leaves an existing table as it is, so a change to one means starting from a new file, while a table the file lacks, as `maps` once was, is added to it. That is one reason a robot's name is a table, `names`, and not a column of `robots`; the other is that a name is nothing the robot sent. The spec has no name for a robot, only the board serial of its login, which is what the UI called a robot before and still does by default: a row in `names` is a robot that was given a name, `save_name` with `None` deletes it, and the `name` a robot is read with is then NULL. Nothing keeps two robots from one name. A map's name is a table of its own for the same reasons, `map_names`, by the user's request (2026-10-18) that maps can be named: a row is a map that was given a name, by its `id` in `maps`, `save_map_name` with `None` deletes it, and a map without one goes by the start time of its run on the page (see "Map names" below). Nothing keeps two maps from one name either. The `events` table is the append-only event log: `add_event` inserts a row whose `id` orders them. Its `kind` is a word only this server chooses (`login`, `disconnect`, `call`, or the envelope type of a message the robot sent) and its `service` is whatever name the robot sent; the two are separate columns so that a message for a service named `login` cannot pass for a login. Nothing prunes the table: rows leave it only with their robot. `events()` reads rows back for the web UI, as stored. It gives one robot's, through the `events_by_robot` index, because the UI shows events only on a robot's own page; the store tests still check the file through a second connection. The `maps` table gets a row from `save_map` for each `maps.create`, with the whole body in `map_json`; the user asked (2026-10-08) for maps as JSON objects in a table of their own. The two binaries stay in the object as the Base64 text the robot sent, where the spec suggests decoding them into binary storage, so this is the one place they are kept: the event of the same upload has them redacted. A row is an upload, and a `rank_uuid` is one upload: a real robot (firmware 1.7.0) sent a map at every pause of a run and one at its end, each under a new `rank_uuid` and all with the run's `timing.start`, and the spec has a robot send an upload again under its `rank_uuid` when its connection dropped before the answer, which a server SHOULD take for the one it has (section 7.3). So the `maps.create` handler stores no map of a `rank_uuid` that the robot has a map of in the file already, and answers it 201 as it did the first; `has_map` asks that through the `maps_by_rank_uuid` index, which is on the expression `_RANK_UUID`, written the same way in the query so that the index is used. A map whose `rank_uuid` is not text is stored each time, and so is one whose `has_map` failed, which is logged: a map twice in the file is better than one not in it. `maps()` lists one robot's, through the `maps_by_robot` index, each without its two binaries and with its `name`: `_MAP` takes the binaries out with `json_remove`, which leaves every number as the text it was sent as, and reads the name out of `map_names` with a subquery, where a join would have every column the two tables share named by its table in each query that lists maps. SQLite still reads each listed map whole to do that, on every poll of a robot's page, which is why the web UI lists few at a time. `floorplan_maps()` gives the same way those of a robot's maps that a floor plan of its was made of and that are older than the map it is told, which is how the page has the map of a floor plan that is not among those few. `map()` gives one row as it is stored, without a name, and only for the robot it is asked of. `map_names()` gives the `rank_uuid` and the name of each of a robot's maps that was given one, for the events of their uploads, which name a map by its `rank_uuid`; SQLite reads each of those maps whole for it, and they are as few as the maps an owner names. The `floorplans` table is what the server remembers of the floor plans a robot keeps (see "Floor plans" below): a row for each `rank_uuid` a robot accepted from this server, with the `id` of the map it was made of, which is not copied and stays in `maps` as long as the robot does. `save_floorplan` upserts one, so a floor plan that is made again is the same row with its later map and time, `delete_floorplan` takes one out, and `floorplans()` lists one robot's, the last accepted first. The `tracks` table is the same for the zones and the no-go lines of those floor plans (see "Zones and no-go lines" below): a row for each `track_uuid` a robot accepted from this server, with the floor plan it is of, its `type`, a zone's name and mode, and what was drawn for it as `shape_json`, which the robot was sent only as a picture and could not give back. `save_track` upserts one, `delete_tracks` takes some out, and `tracks()` lists one robot's, by floor plan, its zones first, in the order they were first noted, which is their `rowid`: the upsert of a zone that is changed keeps its row, so a zone keeps its place, and with it its colour on the page (see "Zones and no-go lines" below), whatever it is renamed or redrawn to. A `VACUUM` may number the rows anew, which nothing here runs. A floor plan's tracks go with it: `delete_floorplan` takes them out with it, and `save_floorplan` takes out those of the floor plan it notes, since a promotion comes with no tracks. Those of the floor plan an update replaces go to the one that replaces it, since a robot keeps them in effect for it (section 6.3, which the user extended to say so on 2026-10-18); the spec has that not verified against firmware 1.7.0, and no update has been sent to a real robot through this server. They keep their rows, and with them their places and their colours. That the tracks the new floor plan had, if it was one already, are not kept is my reading, as what a robot does with them is not known. Reads and writes are synchronous and run inline in the event loop: each is one autocommitted statement, a locked file is waited on for at most `_BUSY_TIMEOUT`, and the default rollback journal is kept rather than WAL so that the file also works on a Docker bind mount. Two writes are more than a statement. `delete` takes a robot's rows out of every table in `_TABLES` in a transaction it begins itself (`BEGIN IMMEDIATE` inside `with self._db`, which commits it or rolls it back), so a robot is deleted from all seven or from none. `save_floorplan` and `delete_floorplan` go through `_change`, which does the same with the statements it is given, so a floor plan and its tracks go together, and where a floor plan takes the place of another the old row goes and the new one comes, or neither. A table added to the schema has to be added to `_TABLES`, which a test checks against the file. The connection has `secure_delete` on, so what is deleted is zeroed in the file and not left in its free pages; the file does not shrink. `delete` logs its failure and says whether it wrote, like `_write`. A failed write, including a body one of those checks refuses, is logged and swallowed inside `Store`, so a storage problem never ends a session. `_write` says whether it wrote, which `save_map`, `save_name`, `save_map_name`, `save_track` and `delete_tracks` pass on, and `_change` says the same of its transaction. The page that sent a name is told 503 when it was not written. A map is the one write a robot waits to hear of: the `maps.create` handler answers 201 only for a map that is in the file, 500 for one that is not, and 400 for a body that is not an object. The spec names no code for a failure, only that the robot takes any code but 201 for a failed upload, which it logs and never sends again (section 7.3), so a map the file did not take is lost; neither code has been sent to a real robot. A failed read raises `StoreError`, as does failing to open the file, which `main` turns into a startup error. `watch` has a function called with a robot after every write of something of it, by `_write`, `_change` and `delete`, whether or not the write was done, since a robot logs in and out with a write: that is how `Mqtt` hears of a change, and it is called inside the write, so it does no more than take note. `last_event` and `alerts` are for it as well: the `id` of the last event of any robot, and the `robots.error_codes` and `robots.notify` messages of every robot after an `id`, oldest first, through the primary key.

**Web UI** (`web.py`, `static/`). `Web` is a second listener in the same event loop, over plain HTTP. `_serve` in `__main__.py` starts it beside the `Server` when the `web` setting is on; `Server` knows nothing of it, so the robot-protocol tests never open it. It takes three things from the `Server`: the `Store`, which it reads rows from and writes nothing to but the names of robots and maps, the floor plans and their tracks, `Server.sessions` for whether a robot is connected (`Session.since` exists only to be shown here, and `Session.firmware` for that and for the login event) and for the session a command is sent on, and `Server.delete`. From `_serve` it takes the `Mqtt` too, where there is one, for the indicator of Home Assistant (see "Home Assistant" below). The HTTP side is written by hand because the project has no web framework among its dependencies: `GET` and `HEAD`, and `POST` alone for the paths in `_posts` (a command, the schedule, the settings, a floor plan, a zone or no-go lines, the name of a robot or of a map, the deleting of a robot), one request per connection (`Connection: close`), and no request body is ever read. `_TIMEOUT` is how long a connection has to send its request and, separately, to take the answer; the wait between the two is a command's for its robot, which `_COMMAND_TIMEOUT` limits. The files in `static/` are read once at startup into a table keyed by request path, so no file name is ever built from a request; `pyproject.toml` lists them as package data, which the Docker image relies on. Being read once, they make a page that a server started with other files gave out of date, so `Web` keeps their version, `_version`: the first 16 hexadecimal digits of a SHA-256 of every file of `_PAGES` with its path and its length, `mtp-fs.js` included, which the server reads as it serves it. It writes that into `index.html` in place of `{version}` (`_VERSION_MARK`), in a `meta` named `deorbit-version`, and gives it as `version` with every answer of `/api/robots` and `/api/robot` (see "Toasts" below). The JSON API gives what the store reads (true and false as `1` and `0`, JSON as text) and the page interprets it; a robot is named in the query string because a vendor or serial may hold `/` or be `..`. `/api/robot` gives a robot together with its latest events and maps, as many as the `events` and `maps` parameters say, with all its floor plans and all their tracks, and as `map_names` with the `rank_uuid` and the name of each of its maps that was given one, for the events of uploads. It asks the store for one more of each than that, which is how it knows whether to say there are `more` and `more_maps`. Where there are more maps, it also gives those older ones that a floor plan was made of, as `floorplan_maps`: the page shows a floor plan as the map it was made of, so that map has to come however old it is. A number outside 1 to `_MAX_EVENTS`, or to `_MAX_MAPS`, is answered with status 400, so `EVENTS_MAX` and `MAPS_MAX` in `app.js` have to match, which a test checks. `/api/map` gives one map whole, named by its robot and its `id`; an `id` that is no number a row can have is answered 404 like any other map that is not there, and has to be turned away before the store, because `sqlite3` raises an `OverflowError`, which is no `sqlite3.Error`, for a number beyond 64 bits. A robot has a page only once it has a row in `robots`, so the events of one that logged in and sent neither a state nor a heartbeat are in the database but not in the UI.

`POST /api/name` names the robot in its query string and gives its `name` there too, so this request has no body to read either. `_name` makes one line of it (white space around it gone, a space wherever there was white space within) and refuses more than `_MAX_NAME` characters, or a control character, with a 400; these limits are this server's choice. No name, or none left, takes the robot's name away. `_rename` answers 200 with the `name` as it is kept, 404 for a robot without a row in `robots`, since a name for one would be a row nothing reads, and 503 for a name the store did not write. It sends the robot nothing and adds no event, so the robot need not be connected. It is behind `_own_page` like a command. The page's `NAME_MAX` must be `_MAX_NAME`, which a test checks.

`POST /api/map_name` is the same for a map: the query names the robot, the map by its `id` as `/api/map` has it, and the `name`, which `_name` makes and checks as it does a robot's, under the same `_MAX_NAME`, which is my choice. `_rename_map` answers 200 with the `name` as it is kept, 404 for an `id` that is no map of the robot's in `maps`, which it reads whole to know, as `_floorplan` does, and 503 for a name the store did not write. It sends the robot nothing and adds no event either, and is behind `_own_page`. The robot knows nothing of a map's name, and that holds for a floor plan too, which is called what the map it was made of is called.

**Deleting a robot** (`Server.delete`, `Web._delete`, `forget` in `app.js`). The user asked (2026-10-08) that a robot can be deleted, with all its data "from db and filesystem". The database is the only place this server writes anything of a robot. The one other file that is a robot's is its key under `keys`, which the operator put there; that the request covers it is my reading, and it is what makes a deleted robot stay away where logins are verified. `POST /api/delete` names the robot in its query string, has no body and is behind `_own_page`. `_delete` answers 404 for a robot without a row in `robots`, as `_rename` does, so neither the events of a robot that has no page nor the key of one that never connected can be deleted through it; 200 with `{}` once the robot is gone; and 503 with an `error` when it is not.

`Server.delete` does three things, in an order chosen for what a failure leaves behind. First the key file and the key in memory, when `keys` is set: a file that cannot be removed is an `OSError` (the 503), raised with nothing else touched, which is what a robot gets whose key is on the read-only mount `docker-compose.yml` suggests; and with the key gone first the robot cannot log in again during the rest. Then it closes every session of the robot's and waits for their tasks: a session writes to the store until `run` returns, its `disconnect` last, and a row written after the delete would be left over. It finds them in `_running`, which `_handle` keeps from the handshake to the end of `run`; `sessions` would not do, because a session that a newer login replaced is out of it before it has ended. Last, with nothing awaited since no session was found, `Store.delete`. If that fails (the other 503) the key is gone and the session ended while the rows are all there, so the robot is still listed and asking again finishes the job. Without `keys` nothing keeps a deleted robot out: it logs in again as a new one, and the loop in `delete` is for one that did so while its older session was waited for.

On the page, Delete is beside Rename at the top of a robot's page, by the user's decision (2026-10-08), so `nameLine` draws it and it is there whichever tab is shown. It asks first, in a popover (see "Popovers" below), with what will go, and Delete it there has `forget` send the request and, at a 200, set the address to the list. The view's `deleting` holds whether the server has yet to answer; how the request went is a toast, which outlives the page when the robot is gone.

Save sends each setting whose field holds other than what the robot last gave (`edited`), one after the other, since the spec has no action that changes more than one, and stops at the first the robot does not take. It is held back with `aria-disabled` while no field is changed, which each field tells it of as it changes (`changed`), since no field draws the page anew, and while the robot is asked anything of the settings. A toast says how it went: of one setting as that setting's, of more that the robot accepted them, and of a failure which one failed. Those the robot took are read again, since the answer to a change is `{}`; the fields of the others keep what was chosen, so Save sends them again. The fields are disabled while the robot is asked anything of the settings, so that nothing is chosen that a reading would then drop or a Save not send.

The view's `settings` holds the connection they were last read of, by its `since`; the settings being read or saved, a list that holds the buttons and the fields back while it is not `null`; what the robot gave for each, by name (`shown`); and what the field of each holds (`drafts`), made anew of what the robot gave whenever that setting is read. A toast says why a setting could not be read, and how a Save went. Reading them all is three calls to the robot and six rows of its events, so, unlike the schedule, they are read only once the Settings tab is shown (`settingsDue`, from `show` and `choose`), and then once for each connection, one after the other; that is my choice.

The UI has no authentication, and by the user's decision (2026-10-08) commands do not wait for one: whoever can reach the UI can command a robot. What stops another website from doing so through a visitor's browser is `_own_page`: a command must carry an `Origin` whose host and port are those of its `Host`. A browser sends `Origin` with every `POST`, so a request without one is refused as well, which is why `curl` needs `-H 'Origin: ...'`, and a reverse proxy has to pass `Host` through. The check does not stop DNS rebinding, where a site makes a name of its own resolve to this server: that would take a list of the server's own names, or a login.

**Home Assistant** (`mqtt.py`). The user asked (2026-10-19) for an integration with Home Assistant over MQTT, once its options had been explored, and chose aiomqtt for the client, which made it a third dependency, where the HTTP side is written by hand; and, for a first version, the vacuum, its sensors, the zones as rooms and the alerts as events, but not the map's picture or the settings. The rest is mine. `Mqtt` is made by `_serve` where `mqtt_host` is set, before `Web`, which is given it, and is as unknown to `Server` as `Web` is, and takes the `Store` and `Server.sessions`. It keeps one connection to the broker in a task of its own (`_run`), tried again every `_RETRY` seconds while the broker cannot be reached and after a connection ends, and logs why once until the reason changes, so a broker that is away does not fill the log. Nothing of it ends the server: an exception it did not foresee is logged and the connection tried again.

What it publishes is made from the database, as the web UI's page is. `Store.watch` has `_changed` called with a robot after each write of something of it (see "Storage" above), and the robot is published anew (`_update`): each retained message of the robot's is made as it now is (`_wanted`), and published only where it differs from what the broker holds (`_sent`), so a heartbeat publishes nothing. A robot is published once it has a row in `robots`, as the UI shows one, and one that has none any more, being deleted, has its retained messages taken away by empty ones. At each connection, and when Home Assistant says it has started (`online` on `<prefix>/status`, its birth message), every robot is published again, what the broker held being taken as not known (`None` in `_sent`), since a broker may lose what it retains; a robot announced before and deleted since is among them, so it is taken away then. One that was deleted while the server was down is not, which is a gap.

The topics are under `mqtt_topic` (`deorbit`): `status`, this server's `online`, or `offline` as it stops and as its last will; and under each robot's `_node` (its vendor and serial joined by `_`, where any character but a lowercase letter or a digit is made `_` and a hash of the two is put after them, so that two robots do not come to one), `availability` (`online` while it has a session), `vacuum` (`state`, `fan_speed` and `segments`, as Home Assistant's MQTT vacuum reads them), `state` (`battery`, `charging`, `docked`, `errors` and `connected`, which the sensors read with templates), and `alert` and `notification`, which are not retained. Home Assistant publishes to `command`, `fan_speed` and `clean_segments`. The retained ones and the events are published at QoS 1. A robot is one device of device discovery at `<prefix>/device/deorbit_<node>/config`: the vacuum, named as the device is, with the features start, pause, stop, return_home, locate and fan_speed (`status`, which only gave a status text, is left out); the sensors Battery, Charging, Docked, Errors and Connected; and the event entities Alert and Notification. Every entity is available while this server and the robot both are (`availability_mode: all`), but for Connected, which is available while this server is. The device is named as the web UI calls the robot; its manufacturer is Neato for the vendor `n` and Vorwerk for `1` and `2`, by the hosts section 2 of the spec gives those vendors' clouds, and it has none for another vendor; its software version is the firmware of the robot's last connection since the server started.

The vacuum's state is `activity`: `error` and `paused` for those states, `cleaning` for a robot busy cleaning or in `cleaning_standby`, `returning` for one busy docking, and otherwise, idle or busy with something else such as a software update, `docked` or `idle` by `is_docked`. The Errors sensor is the codes of the robot's errors, or `none`, cut to the 255 characters Home Assistant takes; a charge that is not a finite number is `null`, which the template writes as `None`, an unknown state. A `start` resumes a robot whose last state says it can resume, which is what Home Assistant's start does with a vacuum that is paused, and otherwise starts on no floor plan in the mode of the fan speed, with `normal` navigation; the fan speed is `eco`, as the web UI's Start, until Home Assistant sets another, and is kept in memory, so a restart sets it back. `stop` is a cancel and `locate` a Find me. Each is sent through `Session.call` as the web UI sends a command, in a task of its own (`_calls`), and what the robot answers is logged where it is not 200, as is a robot that is not connected. A command that the broker retained is ignored, since it would be carried out again at every connection.

The segments are the zones of the floor plans in `floorplans`, by `track_uuid`, under the zone's name, and where the robot has zones of more than one floor plan, with the floor plan's name in brackets after it: what its map is called, or when that map's run began, written as the web UI writes it but in the zone of the `timezone` setting. Home Assistant has the user map them to its areas, and asks again when they change. A `clean_segments` sends one `cleaning.start` with a run for each zone given, in that order and each once (`commands.cleaning`, which checks the runs as those of an event of a schedule are): each zone in its own mode, which is what it was given one for, with `normal` navigation, and minding the floor plan's no-go lines where the server had the robot keep some. Refused, with a warning, are segments that are not a list of strings, a zone that is no zone in `tracks`, zones of more than one floor plan (section 6.1), and a robot whose last state says it is not on its base, as the menu of the Start button holds the floor plans back then.

The alerts and the notifications are read out of the event log (`_tell`, with `Store.alerts`) after the last event looked at, which is `Store.last_event` at each connection, so what happened before, or while there was no connection, is not told. A `robots.error_codes` is an event of Alert of its severity, `warning`, `error` or `critical`, with its `code`, and one of another severity is not told; a `robots.notify` is an event of Notification whose type is its `message_code` where section 7.1 of the spec lists it, and `other` for any other code, such as that of an alert of the severity error, with its `code` and its `payload`. An entity's event types have to be listed in advance, which is why the codes the spec does not list are `other`.

The user asked (2026-10-19) for an indicator of the status of the connection to Home Assistant, "similar to 'live' indicator of server connection at top right of the page". The rest is mine. What it shows is this server's connection to the broker, which is all the server knows: Home Assistant's birth and last will on `<prefix>/status` are not retained by default, so whether Home Assistant itself is there is not known at a connection. `Mqtt.status` gives it as `connected`, which `_connected` sets where it logs the connection and `_run` clears as the connection ends, and `error`, which is `_failure`: why the last try failed, the text the log gave, `None` before a try has failed and once one has succeeded. An exception that was not foreseen gives a text of its own that points to the log. `Web` gives that as `home_assistant` with each answer of `/api/robots` and `/api/robot`, and `null` without an `Mqtt`. On the page it is a pill of the `live` look after the server's (`#home-assistant`, `setHomeAssistant`), named Home Assistant, and HA on a screen up to 480 pixels wide; it is hidden until an answer has a `home_assistant` that is not `null`, so a server without a broker never shows it. Its dot is green while the server is connected, and does not beat, as the server's does, so that only one dot on the bar beats; red with the pill, as the server's is, once a try has failed; and quiet while the server tries for the first time, and while the server cannot be reached, which makes it not known. Its `title` and `aria-label` say which, and why a try failed; its text stays the name, which is the one difference from the server's, whose text says how it is.

On Python 3.11, `asyncio.wait_for`, which aiomqtt waits for the broker with, lets a cancellation go by when what it waits for comes at the same time, and the task goes on. A `TaskGroup` then waits for good, which hung a test's cleanup about one time in two, and would hang a server that stops. So `_connected` runs the publishing and the receiving as two tasks and waits for either to end, and `_end` cancels a task again every `_END_AGAIN` seconds until it has ended; `stop` gives the client `_STOP_TIMEOUT` to say goodbye to the broker first.

**Configuration.** The `Config` dataclass in `config.py` is the single source of settings and their defaults. `load` in the same module fills it from a YAML file whose keys are the field names, converting values by each field's annotation, so a new `Config` field of an existing type (`Path`, `str`, `int`, `float`, `bool`) is settable from the file with no further code. Relative paths are resolved against the file's directory. The only command-line option is `-c/--config`; a missing file is an error unless it is the default `./deorbit.yml`, in which case `Config()` is used as is. The `deorbit.yml` at the repository root is an example listing every setting at its default, and the README's table of settings repeats it; update both when a field is added.

`generate_certs` is acted on by `main`, not by `Server`, which always expects the files to exist. An empty `public_address` is filled in by `main` the same way, and only when `web` is on, since nothing but the web UI reads it. Likewise `web`, `web_host` and `web_port` are acted on by `_serve` and `Web`, and the `mqtt_` settings by `_serve` and `Mqtt`. `load` refuses an `mqtt_topic` or an `mqtt_discovery_prefix` with a wildcard or an empty level, since each begins topics that are subscribed to. When `cert` and `key` are both missing, `main` calls `certs.generate` for `certs.DEFAULT_HOSTS` (`orbital.deorbit`); when only one is missing it exits, because generating would overwrite the other.

**Console output.** All message printing goes through `Session._trace`, which redacts the keys in `_REDACTED_KEYS` (signatures, map binaries) unless the `full` setting is on. Heartbeats are logged at DEBUG, everything else at INFO or above.

## Protocol constraints that are easy to break

These come from the spec and are not all enforced by tests:

- The server must never send an `event` to the robot — only `request` and `response`. An event makes the robot drop the connection.
- `robots.notify` arrives as a `request` but must not be answered. `peer.state` and `robots.error_codes` are events and are not answered either.
- A frame's header and payload must go out in one write (`encode_frame` returns them joined), and writes on a connection must not interleave (`Session._send` holds a lock).
- The robot disconnects after 70 seconds without a frame, and its own requests time out after 30 seconds, so handlers must reply promptly. If a handler ever needs to do slow I/O, it can no longer run inline in the receive loop.
- The login response has no `type` or `id`; a non-200 `code` makes the robot disconnect and retry.

## HTTP API

What `web.py` answers besides the files of `static/`, all of it JSON. The page is its first user, and the README does not mention it. A port that is already taken stops the server at startup.

| Address | Content |
| --- | --- |
| `GET /api/robots` | every robot without its `state_json`, ordered by vendor and serial |
| `GET /api/robot?vendor=V&serial=S` | one robot as `robot`, with its `state_json`, its latest 25 `events` and its latest 10 `maps`, both newest first, its `floorplans` and the older maps those were made of as `floorplan_maps`, the `tracks` of its floor plans and the `map_names` of its maps, or status 404; with `events=N` as many events as that, up to 1000, and with `maps=N` as many maps, up to 100 |
| `GET /api/map?vendor=V&serial=S&id=N` | one map of that robot as `map`, whole, or status 404 |
| `GET /api/setup` | what "Bind a robot" needs: the `address`, which is `public_address` as set or as found at startup and empty for none, and the `ca`, the text of `ca.crt` or `null` |

A robot has the columns of the `robots` table (see "Database" below), as stored, its `name` from the `names` table, `null` when it was given none, then the fields of its state that the pages show, and a `session`: `null` for a robot that is not connected, otherwise its `address`, `firmware` and the time `since` when it has been connected. So the page shows the address and firmware of a connection only while it lasts; those of earlier connections are in the robot's login events. The fields are read out of `state_json`:

| Field | Where in the state |
| --- | --- |
| `state`, `action`, `errors` | the fields of those names: what the robot is doing, such as `idle`, and its errors, `null` when it reports none |
| `can_start`, `can_cancel`, `can_pause`, `can_resume`, `can_return_to_base` | `available_commands` |
| `is_charging`, `is_docked`, `charge`, `base_type`, `is_quickboost`, `quickboost_estimate` | `details`; `charge` is a percentage |
| `base_error`, `bag_status`, `is_extracting` | `cleaning_center` |
| `autonomy_states` | `autonomy_states`, whole |
| `autonomy_started_on_base` | the `started_on_base` of `autonomy_states` |
| `autonomy_cleaning_start`, `autonomy_undocking`, `autonomy_active_cleaning_session`, `autonomy_docking_for_suspended`, `autonomy_docking_successful_suspended`, `autonomy_suspended_charging_start`, `autonomy_undocking_after_suspended`, `autonomy_active_cleaning_after_suspended`, `autonomy_docking`, `autonomy_docking_verify_base`, `autonomy_docking_successful` | the other fields of `autonomy_states`: when the robot reached each step of its run, in seconds since 1970 by its own clock, or -1 for a step it has not reached |

True and false are given as 1 and 0, an object or an array as JSON text, and a field the state lacks as `null`. An idle robot sends no autonomy states, which leaves theirs `null`. An event has the columns of the `events` table, as stored, and `more` says whether the robot has older events than were given. A map has the columns of the `maps` table and its `name` from the `map_names` table, `null` when it was given none, and `more_maps` says the same of the maps. With a robot, the `map_json` of each map lacks the two binaries, which are most of it; `/api/map` gives the row as it is stored. A floor plan has the columns of the `floorplans` table, and a robot comes with all of its own, the one it accepted last first. `floorplan_maps` are the maps those were made of that are older than the `maps` given, newest first and each as `maps` gives one, so that every floor plan comes with its map; it is empty when `more_maps` is false. `map_names` gives the `rank_uuid` and the `name` of each of the robot's maps that was given one, of any age, the oldest map first, since the event of an upload names its map by its `rank_uuid`. The answers of `/api/robots` and `/api/robot` carry the server's time as `now`, and as `version` the version of the page the server serves, 16 hexadecimal digits that are others whenever the server is started with other files in `static/`, and as `home_assistant` whether the server is connected to Home Assistant's MQTT broker: `null` where `mqtt_host` is not set, and otherwise `connected`, true or false, and `error`, why the last try to connect failed, or `null` before one has and while connected. The page asks for the latest 25 events and 10 maps, and for that many more each time it is asked to show older ones.

A command is sent with `POST /api/command?vendor=V&serial=S&command=C`, where `C` is `start`, `pause`, `resume`, `cancel`, `return_to_base` or `find_me`, which has the robot make the sound it is found by, and a start may come with `run=JSON` (see below). The request has no body and needs the `Origin` header a browser adds, naming the host it is sent to:

```sh
curl -X POST -H 'Origin: http://localhost:8080' 'http://localhost:8080/api/command?vendor=n&serial=SERIAL&command=pause'
```

When the robot answers, the status is 200 and the JSON holds the `ability` that was invoked with the robot's own `code` and `body`, and `sent`, the server's time when the command went out, which a later `state_at` of the robot is after; a `code` of 200 is the robot accepting the command. Otherwise the JSON holds an `error`, and the status is 403 for a request from another site, 400 for a command that is not one of the six or a `run` the server does not take, with an `error` that names what is wrong, 409 for a robot that is not connected, 504 for one that did not answer in time, which is 10 seconds, and 502 for one whose connection ended first.

Without a `run`, a start cleans on no floor plan, in `eco` mode with `normal` navigation. A `run` is one run as an event of the schedule has them (see below): its `settings`, a `mode` of `eco`, `turbo`, `auto` or `max` and a `navigation_mode` of `normal` or `gentle`, and a `map` that is `null` for no floor plan or has the `rank_id` of one, a `track_id` that is `null` for the whole of it or a zone, and `nogo_enabled`. A robot answers a start on a floor plan or a zone that it does not have with a `code` of 422.

```sh
curl -X POST -G -H 'Origin: http://localhost:8080' 'http://localhost:8080/api/command?vendor=n&serial=SERIAL&command=start' \
  --data-urlencode 'run={"settings":{"mode":"turbo","navigation_mode":"normal"},"map":{"rank_id":"414fb561-91a7-4a95-8fc7-200169d2d5af","track_id":null,"nogo_enabled":true}}'
```

A schedule is read and changed with `POST /api/schedule?vendor=V&serial=S&action=A`, which needs the same `Origin` and is answered the same way, with the `ability` it invoked and the robot's `code` and `body`:

| `action` | With | Invokes |
| --- | --- | --- |
| `show` | nothing | `scheduling.show`; the `body` of the answer is the schedule, with its `events` |
| `add` | `event=JSON`, an event without an `id` | `scheduling.add`; the robot gives the event its `id`, which only `show` tells |
| `update` | `event=JSON`, an event with the `id` of the one it replaces | `scheduling.update` |
| `delete` | `id=N` | `scheduling.delete` |

```sh
curl -X POST -H 'Origin: http://localhost:8080' 'http://localhost:8080/api/schedule?vendor=n&serial=SERIAL&action=show'
curl -X POST -G -H 'Origin: http://localhost:8080' 'http://localhost:8080/api/schedule?vendor=n&serial=SERIAL&action=add' \
  --data-urlencode 'event={"enabled":true,"days":["mon","wed","fri"],"time":"09:30","command":{"ability":"cleaning.start","runs":[{"settings":{"mode":"eco","navigation_mode":"normal"},"map":null}]}}'
```

An event is the one of the specification, in the address like everything else of a request: `enabled`, true or false; `days`, one or more of `mon`, `tue`, `wed`, `thu`, `fri`, `sat` and `sun`; `time`, from `00:00` to `23:59`; and a `command` whose `ability` is `cleaning.start` and whose `runs` are one or more runs. A run has its `settings`, a `mode` of `eco`, `turbo`, `auto` or `max` and a `navigation_mode` of `normal` or `gentle`, and a `map` that is `null` for no floor plan or has the `rank_id` of one, a `track_id` that is `null` or a zone, and `nogo_enabled`. More runs than one must all be of the same floor plan. An `id` is a string of digits. A request the server does not take is answered 400 with an `error` that names what is wrong. A schedule also says whether it is on as a whole, which no command changes, so the page only says so when a robot gives its schedule as off.

A robot's settings are read and changed with `POST /api/settings?vendor=V&serial=S&action=A`, which needs the same `Origin` and is answered the same way, with the `ability` it invoked and the robot's `code` and `body`. `A` is the name of a setting, which reads it and invokes `settings.A`, or that name after `set_` with `value=JSON`, which changes it and invokes `settings.set_...` with the fields of the value:

| Setting | Read, the `body` of the answer | `value` of a change |
| --- | --- | --- |
| `robot_language` | `language`, `available_languages`, and from some robots `gender` | `{"language": L}`, `L` one of the `available_languages` |
| `cleaning_options` | `force_floorplan` | `{"force_floorplan": B}` |
| `ota_updates` | `auto` | `{"auto": B}` |

```sh
curl -X POST -H 'Origin: http://localhost:8080' 'http://localhost:8080/api/settings?vendor=n&serial=SERIAL&action=ota_updates'
curl -X POST -G -H 'Origin: http://localhost:8080' 'http://localhost:8080/api/settings?vendor=n&serial=SERIAL&action=set_ota_updates' \
  --data-urlencode 'value={"auto":false}'
```

`B` is true or false. A change is answered by the robot with an empty `body`, so it is read again to see it. A request the server does not take is answered 400 with an `error` that names what is wrong. A factory reset and the sounds, which the spec has among the settings, cannot be asked for.

A robot is told to keep a map as a floor plan, or to drop a floor plan, with `POST /api/floorplan?vendor=V&serial=S&action=A`, which needs the same `Origin` and is answered the same way, with the `ability` it invoked and the robot's `code` and `body`:

| `action` | With | Invokes |
| --- | --- | --- |
| `promote` | `map=N`, the `id` of a map of that robot's | `maps.promote_floorplan`: the robot keeps the map as a new floor plan, with no zones and no no-go map |
| `update` | `map=N`, and `old_rank_uuid=U` | `maps.update_floorplan`: the robot keeps the map in place of the floor plan it knows as `U`, with that one's zones and no-go lines |
| `demote` | `rank_uuid=U` | `maps.demote_floorplan`: the robot deletes the floor plan it knows as `U`, with its zones and no-go lines |

```sh
curl -X POST -H 'Origin: http://localhost:8080' 'http://localhost:8080/api/floorplan?vendor=n&serial=SERIAL&action=promote&map=5'
curl -X POST -H 'Origin: http://localhost:8080' 'http://localhost:8080/api/floorplan?vendor=n&serial=SERIAL&action=demote&rank_uuid=414fb561-91a7-4a95-8fc7-200169d2d5af'
```

The floor plan has the `rank_uuid` of its map, the map's two binaries and the place of its base, and says it was made when the map's run ended, its `timing.end`. A `code` of 200 is the robot accepting, and only then do the `floorplans` that come with the robot change, and with them the `tracks`: those of a floor plan that is promoted or demoted are gone from them, and those of one that is replaced are of the floor plan that replaces it. The `floorplans` are what this server had the robot make, not what the robot holds, which it cannot be asked for. So `U` need not be one of them: a floor plan the robot has from elsewhere, such as the `persistent_rank_uuid` of a map or the `rank_id` in its schedule, is named the same way. The status is 404 for a map that is not in the database, 400 with an `error` that names what is wrong for an `action` that is none of the three, a `U` that is not a UUID or a map that lacks what a floor plan takes, such as a `timing.end` written `YYYY-MM-DDTHH:MM:SSZ`, and 503 when the robot accepted and the database could not be written, after which the request can be sent again. The other statuses are those of a command.

A robot is told to keep a zone of a floor plan or its no-go lines, or to drop either, with `POST /api/track?vendor=V&serial=S&action=A`, which needs the same `Origin` and is answered the same way, with the `ability` it invoked and the robot's `code` and `body`:

| `action` | With | Invokes |
| --- | --- | --- |
| `zone` | `rank_uuid=U`, a floor plan of `floorplans`; `zone=JSON`, its `name`, its `cleaning_mode` and its `rect`; and to change a zone its `track_uuid=T` | `maps.save_track`: the robot keeps the zone, new or in place of `T` |
| `nogo` | `rank_uuid=U` and `lines=JSON`, a list of lines | `maps.save_track`: the robot keeps the lines as the floor plan's no-go lines, in place of those it had |
| `delete` | `track_uuid=T` | `maps.delete_track`: the robot deletes the zone or the no-go lines it knows as `T` |

```sh
curl -X POST -G -H 'Origin: http://localhost:8080' 'http://localhost:8080/api/track?vendor=n&serial=SERIAL&action=zone&rank_uuid=414fb561-91a7-4a95-8fc7-200169d2d5af' \
  --data-urlencode 'zone={"name":"Kitchen","cleaning_mode":"eco","rect":[980,1010,1060,1075]}'
curl -X POST -G -H 'Origin: http://localhost:8080' 'http://localhost:8080/api/track?vendor=n&serial=SERIAL&action=nogo&rank_uuid=414fb561-91a7-4a95-8fc7-200169d2d5af' \
  --data-urlencode 'lines=[[990,1000,990,1040],[1000,1080,1050,1080]]'
```

A zone is a rectangle and a line goes from cell to cell, each as four whole numbers that are cells of the `rank_binary` of the floor plan's map, counted from 0 from its left and from its top: a zone's top left cell then its bottom right one, and a line's one end then its other. A `name` is 1 to 32 characters, made one line; a `cleaning_mode` is `eco`, `turbo`, `auto` or `max`; and there are 1 to 100 lines, none ending where it starts. A floor plan has 6 zones at most, so a new zone of one that has them all in `tracks` is answered 400, while each of them may still be changed. A new zone gets a `track_uuid` from the server, and a floor plan has one track of no-go lines, which a `nogo` replaces. What the robot is sent for either is a picture of the floor plan's size, two bytes to a cell, with the header of the map's `real_binary` but for its maxval, drawn by the server, in which each cell of the zone or the lines is 1024: the value the spec gives for a zone, and says to use for no-go lines too (see "Zones and no-go lines" above). The map's two binaries have to be PGM files of one size, each with a maxval from 129 to 255. A `code` of 200 is the robot accepting, and only then do the `tracks` that come with the robot change; like the `floorplans`, they are what this server had the robot keep, so `T` need not be one of them for a `delete`. The status is 404 for a floor plan that is not in the database, or whose map is not, and for a `T` that is no zone of that floor plan in it; 400 with an `error` that names what is wrong for anything else the server does not take; and 503 when the robot accepted and the database could not be written. The other statuses are those of a command.

A robot is named with `POST /api/name?vendor=V&serial=S&name=NAME`, which needs the same `Origin` and sends the robot nothing:

```sh
curl -X POST -G -H 'Origin: http://localhost:8080' 'http://localhost:8080/api/name?vendor=n&serial=SERIAL' \
  --data-urlencode 'name=Living room'
```

The answer is 200 with the `name` as it is kept, which is `null` when nothing is left of it or when the request has no `name`. Otherwise the JSON holds an `error`, and the status is 400 for a name of more than 64 characters or with a control character in it, 404 for a robot that is not in the database and 503 for a name the database did not take.

A map is named with `POST /api/map_name?vendor=V&serial=S&id=N&name=NAME`, where `N` is its `id`, which needs the same `Origin` and sends the robot nothing:

```sh
curl -X POST -G -H 'Origin: http://localhost:8080' 'http://localhost:8080/api/map_name?vendor=n&serial=SERIAL&id=5' \
  --data-urlencode 'name=Ground floor'
```

The answer is that of a robot's name, but that the status is 404 for a map that is not one of that robot's in the database. A map without a name is shown by when its run began.

A robot is deleted with `POST /api/delete?vendor=V&serial=S`, which needs the same `Origin`:

```sh
curl -X POST -H 'Origin: http://localhost:8080' 'http://localhost:8080/api/delete?vendor=n&serial=SERIAL'
```

The answer is 200 with an empty object once the robot is gone, 404 for a robot that is not in the database and 503 for one that could not be deleted. The robot is still listed after a 503, so the request can be sent again.

## Database

What is in the `database` file, which is created with its directory at the first start. Times are UTC, written like `2026-10-08T13:55:37.511Z`. The `robots` table has one row per robot that has connected:

| Column | Content |
| --- | --- |
| `vendor`, `serial` | the robot, as the log names it: `[<vendor>/<board serial>]`, both in lowercase |
| `heartbeat_at` | when the robot's last heartbeat arrived; robots send one a minute |
| `state_at` | when the robot's last state arrived |
| `state_json` | that state, whole: the JSON object the robot sent |

Each state replaces the one before it entirely, and `state_json` is empty before the robot has sent one. SQLite's JSON functions read a field out of it, which is how to ask the file, also while the server runs:

```sh
sqlite3 data/deorbit.db "SELECT serial, state_json ->> '$.state', state_json ->> '$.details.charge', state_at FROM robots"
sqlite3 data/deorbit.db "SELECT serial FROM robots WHERE state_json ->> '$.details.is_docked' = 0"
sqlite3 data/deorbit.db "SELECT serial, datetime(state_json ->> '$.autonomy_states.cleaning_start', 'unixepoch') FROM robots"
```

`->>` needs SQLite 3.38 or later; `json_extract(state_json, '$.state')` reads the same from an older one. True and false come out as 1 and 0. The store tests ask the file this way through a second connection.

The `names` table holds the `vendor` and `serial` of each robot that was given a name, and that `name`. A robot that goes by its serial has no row. The `map_names` table is the same for maps: the `vendor` and `serial` of a robot, the `map_id` of each of its maps that was given a name, its `id` in `maps`, and that `name`. A map that goes by when its run began has no row.

```sh
sqlite3 data/deorbit.db "SELECT m.id, n.name, m.map_json ->> '$.timing.start' FROM maps m LEFT JOIN map_names n ON n.map_id = m.id"
```

The `events` table gets a row when a robot logs in, when its connection ends, when the server calls one of the robot's abilities, and for each message the robot sends other than a state and a heartbeat:

| Column | Content |
| --- | --- |
| `id` | a number that counts up: the order the events were recorded in |
| `at` | when the event was recorded |
| `vendor`, `serial` | the robot |
| `kind` | `login`, `disconnect`, `call` for an ability the server called, or the type of the robot's message: `request`, `event`, or `response` for its answer to a call |
| `service` | the service a request or an event was for, such as `robots.notify`; empty for the other kinds |
| `body_json` | the message's body as JSON, empty if it had none; for a login its `address`, its `firmware` and whether its signature was `verified`; for a disconnect the `reason`; for a call what the robot was sent, which names the `ability`; for a response that `ability` and the robot's `code` and `body` |

Signatures and map binaries are replaced by their length, like `<2048 chars>`. A body is read the way a state is, and since nothing prunes the table, this is also how to drop what is older than 30 days:

```sh
sqlite3 data/deorbit.db "SELECT at, body_json ->> '$.message_code' FROM events WHERE service = 'robots.notify'"
sqlite3 data/deorbit.db "DELETE FROM events WHERE at < date('now', '-30 days')"
```

The `maps` table gets a row for each `maps.create`, which a robot sends when a cleaning run ends or is interrupted, but for one with the `rank_uuid` of a map the robot has in the table already, which is that upload sent again:

| Column | Content |
| --- | --- |
| `id` | a number that counts up: the order the maps arrived in |
| `at` | when the map arrived |
| `vendor`, `serial` | the robot |
| `map_json` | the map, whole: the JSON object the robot sent |

Here the object has its two binaries, `rank_binary` and `real_binary` under `map`, each a compressed PGM file as Base64 text. The rest of the object is read the way a state is, and a binary comes out with `base64`, and as a PGM file once it is inflated:

```sh
sqlite3 data/deorbit.db "SELECT id, at, serial, map_json ->> '$.rank_uuid', map_json ->> '$.cleaning_complete', map_json ->> '$.runs[0].state' FROM maps"
sqlite3 data/deorbit.db "SELECT map_json ->> '$.map.real_binary' FROM maps WHERE id = 1" | base64 -d > real_binary
sqlite3 data/deorbit.db "SELECT map_json ->> '$.map.rank_binary' FROM maps WHERE id = 1" | base64 -d | python3 -c "import sys, zlib; sys.stdout.buffer.write(zlib.decompress(sys.stdin.buffer.read()))" > rank.pgm
```

The `floorplans` table gets a row when a robot accepts a map as a floor plan from this server, and loses it when the robot accepts that it is to drop that floor plan, or takes another in its place:

| Column | Content |
| --- | --- |
| `vendor`, `serial` | the robot |
| `rank_uuid` | what the robot knows the floor plan by: the `rank_uuid` of the map it was made of |
| `map_id` | that map, by its `id` in the `maps` table |
| `at` | when the robot accepted it |

A robot has one row for each `rank_uuid`. The table is the server's record and not the robot's: a floor plan the robot was given by anything else is not in it.

```sh
sqlite3 data/deorbit.db "SELECT f.serial, f.rank_uuid, f.at, m.at, m.map_json ->> '$.timing.start' FROM floorplans f JOIN maps m ON m.id = f.map_id"
```

The `tracks` table gets a row when a robot accepts a zone of one of those floor plans, or its no-go lines, from this server, and loses it when the robot accepts that it is to drop that track, or its floor plan goes from `floorplans`, but for one that another takes the place of, whose tracks are then that one's:

| Column | Content |
| --- | --- |
| `vendor`, `serial` | the robot |
| `track_uuid` | what the robot knows the track by |
| `rank_uuid` | the floor plan it is of |
| `type` | `cleaning` for a zone, or `no-go` for the floor plan's no-go lines |
| `name`, `mode` | a zone's name and cleaning mode; `NULL` for no-go lines |
| `shape_json` | what was drawn, in cells of the `rank_binary` of the floor plan's map, from its left and its top: a zone's rectangle as `[left, top, right, bottom]`, or the lines as a list of `[x, y, x, y]` |
| `at` | when the robot accepted it |

```sh
sqlite3 data/deorbit.db "SELECT serial, rank_uuid, type, name, mode, shape_json FROM tracks"
```

A state, a map or a body that is not stored because SQLite could not read it back as JSON is one with a number such as `1e999`, too large for the server to read as a number at all, or with text that is not Unicode.

## Tests

`tests/test_server.py` is end-to-end: a scripted `Robot` talks to a real `Server` over TLS on an ephemeral port, with certificates and a robot key generated once per test class. `ServerTestCase.start(**overrides)` takes `Config` field overrides, which is how tests shorten `heartbeat_interval`, `idle_timeout` and similar. `login()` returns both the wire-side `Robot` and the server-side `Session`, so a test can drive either end. Each test gets its own database file, named after the test, in the class's temporary directory.

`tests/test_config.py` covers the settings file. Its command-line cases call `main()` through a helper that patches out `_serve` and `logging.basicConfig`, so no server is started and no console handler outlives the test; a case that would otherwise generate a certificate does so inside its temporary directory. The helper also puts a mock in place of `local_address`, which finds no address unless a test says so, because the machine the tests run on has whatever address it has; `LocalAddressTests` is the function itself, with a mock for the socket in all but one test.

`tests/test_store.py` drives a `Store` directly and checks what it leaves in the file.

`tests/test_web.py` starts a `Web` beside the `Server` of `ServerTestCase` and speaks HTTP to it over a raw connection, which is what lets it send malformed requests and choose the `Host` and `Origin` of a command; `api()` fails on JSON a browser would refuse. `CommandTests` has the scripted robot answer each command, and relies on the in-order handling the same way to show that a refused request sent the robot nothing. `NameTests` is `/api/name`, with a trigger made through a second connection for a file that takes no write, and `MapNameTests` is `/api/map_name` the same way. `DeleteTests` is `/api/delete`, and the class of that name in `test_server.py` is `Server.delete` itself. A test that deletes a robot while logins are verified starts its server on `registry()`, a copy of the class's directory of keys made for that test, because the class's own is shared by all its tests; a key file that cannot be removed is a patched `Path.unlink`. `ScheduleTests` does both for `/api/schedule`; its one long test is the list of everything `scheduling` refuses, each with the `error` it is refused with. `SettingsTests` does the same for `/api/settings`. `FloorplanTests` is `/api/floorplan` the same way, and stores a map for each thing `floorplan` refuses of one. `TrackTests` is `/api/track` the same way, on a floor plan of 20 by 10 cells, and reads each binary it sends back as rows of cells. `VersionTests` is the version of the page, as `index.html` and the answers give it. `ServeTests` runs `_serve` itself.

`tests/test_mqtt.py` starts an `Mqtt` beside the `Server` of `ServerTestCase`, connected to a `Broker` of the test's own: an MQTT 3.1.1 broker of as much as aiomqtt uses (a connection with a login and a last will, publishing at QoS 0 and 1, retained messages, subscriptions with wildcards, pings), which keeps every message it is given, can send one as Home Assistant would and can drop every connection, so no Mosquitto is needed. `RobotTestCase` has the scripted robot connected, and relies on the in-order handling, as `CommandTests` of the web does, to show that the robot was sent nothing. A test that deletes the robot starts its server on `registry()`, as the web's do. `HomeAssistantTests` of the web gives `Web` a mock of `Mqtt` for its status, and `ServeTests` here has `_serve` give the web UI the real one. The page's script has no automated tests: after changing `static/`, look at it in a browser against a database with robots in several states. `map.js` can be tried without one: under Node, `readBinary` and `paint` take a binary out of the `maps` table and give the pixels, which is how they were checked against the real maps.
